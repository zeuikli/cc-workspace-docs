## 全文摘要

**定位**：將 Loop Engineering 應用於 prompt 自動優化：用評估集的數字作為成功條件，讓 agent 根據失敗案例自動改寫 prompt，直到達到閾值。完整 Python 實作，含防作弊機制。

### 核心概念

**Prompt 優化循環**：loop 重寫 prompt → 針對評估集運行 → 評分 → 重複，直到分數高於閾值。Agent 讀取失敗案例後診斷並改寫 prompt。

### 評估集可靠性等級（從高到低）

1. **Exact match / regex**：最可靠
2. **Classification**：固定標籤比對
3. **Verifiable property**：JSON 解析、數字範圍、程式碼測試
4. **Judge-model 評分**：最後手段，因無硬性錨點

> 規則：把任務盡量推向等級 1/2。每往下一層都引入噪音，讓 loop 可以作弊的空間更大。

### 三種作弊方式（Reward Hacking）

**1. Overfitting（過擬合評估集）**
- 症狀：訓練分數 0.95，但真實場景崩潰
- 修復：**train/holdout 分割**，成功條件只看 holdout，不看 train

**2. Judge-model 自我讚美（Self-praise Collusion）**
- 症狀：judge 和 worker 是同一模型 → agent 學習讓 judge 喜歡的風格而非正確答案
- 修復：**judge 用不同模型**；judge prompt 要有事實錨點（expected answer），不純評「品質」

**3. Metric Gaming**
- 症狀：優化 exact match → 模型只答一個詞；優化長度 → 答案膨脹
- 修復：**多維度評估**（準確度 + 長度懲罰），讓不同方向互相拉扯

### Propose 函數設計（強版本）

```python
def propose(current_prompt, fails, call_model):
    meta_prompt = f"""You are optimizing a prompt. Here is the current prompt:

<current_prompt>
{current_prompt}
</current_prompt>

It failed on these examples:
{fail_text}

First, in one or two sentences, diagnose the SINGLE most common reason
these failed. Then rewrite the prompt to fix that reason specifically.

Rules:
- Keep what already works, change only what addresses the diagnosed failure.
- Do not add instructions that target these exact inputs by content.
  Generalize the fix, do not memorize the examples.
- Output ONLY the new prompt, nothing else."""
```

**關鍵**：Agent 先給出「單一診斷」再改寫，防止每次修補全部問題導致 prompt 膨脹成矛盾指令堆。

### 成本控制：Plateau Detector（高原偵測器）

```python
PATIENCE = 3  # N 次迭代無改善即停止

# 主迴圈中：
if best["score"] <= prev_best + 0.005:
    no_improve += 1
    if no_improve >= PATIENCE:
        print("Plateau for N iterations. Burning money for nothing."); break
else:
    no_improve = 0
```

**Plateau detector 比 iteration cap 更重要**：Prompt 優化通常快速拿到容易的百分點後停滯，10 次迭代固守 0.88 卻每次都消耗整個評估集。PATIENCE 在無改善時立即停止。

### 4 種 Loop 死亡模式

1. **Runaway**：呼叫計數攀升但 holdout 不動。閾值設定不切實際（baseline 0.5 → target 0.99 不可達）
2. **Silent death by overfit（最危險）**：train 分數慢慢上升但 holdout 未動。只看 train 分數的成功條件
3. **Random walk**：score 在同一點抖動不收斂。propose 只改外表，或 temperature 過高
4. **Comprehension debt（最隱晦）**：loop 交付 holdout 0.93 的 prompt，你部署後卻不理解它為何有效 → 過擬合評估集的 prompt 在真實生產上崩潰

### 適用場景

**值得建**：prompt 在生產環境頻繁運行（分類器/提取器/路由器），有標記評估集或容易收集，品質可量化為數字。

**不值得建**：只跑一兩次的一次性創意 prompt → 建評估集的成本無法被使用頻率攤還。

### 核心原則（與 The Loop 一致）

> **「A loop is exactly as good as the part it cannot touch. Build that untouchable part first, and the optimization second.」**

→ 把判斷帶到外部（holdout 評估集 + 事實錨點），agent 無法重寫的部分越可靠，loop 越可信。

## 研究摘要

**TL;DR**：Loop Engineering 應用於 prompt 自動優化：eval 可靠性等級、train/holdout 防過擬合、judge 異模型防自我讚美、PATIENCE 高原偵測器防空燒、診斷優先改寫、Comprehension debt 警告。技術深度最高，適用於高頻生產 prompt 優化場景。

### 核心論點

- **Eval 硬化優先於優化**：先把評估從主觀推向可量化，再建 loop
- **PATIENCE 高原偵測器**：比 iteration cap 更重要的成本控制機制，在無改善時停止
- **診斷優先改寫**：agent 給出「單一診斷」後才改寫，防 prompt 無限膨脹
- **Comprehension debt**：部署自己看不懂的 loop 輸出 = 過擬合未發覺

### 關鍵數據 / 工具

- 完整 Python 實作（evaluate, optimize, propose, history 全部提供）
- PATIENCE = 3（3 次無改善即停，高原早停閾值 0.005）
- 評估等級：exact match → label → verifiable → judge-model
- `.champion.json`：只在 holdout 分數真正提升時覆蓋

### 批判性觀察

- 不是 Fable 5 特定內容；適用於任何 LLM 的 prompt 優化
- PATIENCE 高原偵測器可作為 /goal loop 設計原則（N 次無改善即停）
- Comprehension debt 概念對 unverified_success 閘門是有價值的補充
- 文章比其他批次 Fable 5 文章更具技術深度和代碼品質
- 使用場景限於高頻生產 prompt，對一般工作區規則整合性有限
