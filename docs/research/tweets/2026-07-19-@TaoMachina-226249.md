## 全文

We have already built half an operating system by accident. It is time to build the other half on purpose.

One night, before going to bed, I gave a coding agent a task. It was not a one-shot prompt, but an agent loop designed to keep running. The agent would implement the task, submit its work to a reviewer, pass through a set of workflow checks, and get sent back whenever the result failed inspection.

The next morning, I woke up to more than 30,000 lines of new code for a problem that was not particularly large.

The problem was not simply that the agent had written too much code. It was how those lines had accumulated. To satisfy the reviewer and the workflow checks, the agent kept adding patches on top of problems created in earlier iterations. Each patch introduced new structural issues, which gave the next iteration another reason to add more code. Every modification looked locally defensible, and every checkpoint appeared to be doing its job.

The loop succeeded. The system failed.

Nothing had crashed. The agent had not stopped working. In fact, it had followed the process with remarkable discipline. It kept optimizing the signals available to it, but nothing was responsible for asking whether the current path still served the original problem, whether the reviewer was rewarding the wrong behavior, whether further modification was still worth doing, or whether the failure originated in the implementation, the plan, the evaluation criteria, or the goal itself.

The agent kept "improving." The system kept getting worse.

The agent field is now moving from loops to graphs. A single agent is being decomposed into planners, builders, reviewers, testers, researchers, and tools. Execution is no longer a single line. It branches, runs in parallel, merges, rolls back, and pauses for human intervention.

This transition is necessary. A single loop cannot reliably own planning, execution, review, validation, and recovery at once. Graphs give complex coordination an explicit structure. But once the graph begins to run, a harder class of questions appears: Who decides when a loop must stop? Who arbitrates when policies conflict? What is the system allowed to remember, and who is allowed to write that memory? Most importantly, who has the authority to change the root objective?

Adding more nodes does not answer these questions.

Look through the changelogs of any serious agent framework and the same capabilities keep appearing: checkpoints, retries, human interrupts, permission hooks, sandboxes, and persistent state. They look like framework features. Collectively, they belong to a larger category.

These are not graph features. They are operating-system features.

An agent operating system is already emerging, one patch at a time. We have treated each new capability as an optional extension to the framework, without acknowledging the architectural shift underneath it. Once a system manages state, memory, permissions, failure, recovery, resources, cost, and human authority, it is no longer merely an agent framework. It is becoming an operating system.

The Agent OS described here is not identical to earlier uses of the term "LLM OS." Karpathy's framing treats the model as a new computing core and organizes context, tools, and resources around it. Academic systems such as AIOS focus on scheduling, resource allocation, and isolation between agents. MemGPT approached limited context as a memory-management problem, using hierarchy and paging to give agents continuity beyond a single context window.

Those ideas matter. This essay addresses a different layer.

When multiple models, tools, deterministic programs, and humans work together over time toward a shared objective, who has permission to do what? Who adjudicates failure? Who governs memory? Who stops unproductive execution? Who holds the mission?

This is not only a resource-abstraction problem for a single model. It is a governance problem for a multi-role intelligent system.
1.From Prompts to Graphs, Every Generation Repairs the Last

The evolution of agent architecture can be understood as a chain of repairs.

Prompts solved the problem of expressing intent to a model. A human described a task in natural language, and the model produced a result. But the interaction was largely one-shot. Humans maintained state, sequenced the work, and corrected errors manually.

Workflows turned isolated prompts into repeatable execution paths. Search, summarize, generate, publish. Workflows made action composable, but the path was usually specified in advance. They worked well when the process was known and variation was limited.

Loops introduced feedback. A model could act, observe the result, reflect, modify its approach, and try again. Agents moved from following a predefined sequence to adapting behavior based on outcomes.

But a loop is often described too loosely. A loop is not necessarily an agent, and it is not necessarily a node.

A loop is a feedback topology formed by nodes and edges.

A planner may be one node, a builder another, and a reviewer a third. When the reviewer rejects the output and routes the task back to the builder, the forward execution path and the return edge form a loop. A single agent may contain several internal loops. Multiple agents may also form larger loops across the graph.

Loops introduced feedback, but they did not solve coordination at scale. When a system contains one agent, "think, act, observe, retry" can describe much of its behavior. When it contains three agents, ten agents, or dozens of specialized roles, the central question changes. It is no longer only whether the model can continue reasoning. It is how the roles relate to one another.

Which tasks depend on which others? What can run in parallel? What must wait? Who can veto a result? Which failures propagate downstream? Which nodes may be rerun, and which intermediate outputs must remain stable?

Graphs emerged because these relationships became too complex for linear workflows and single loops to express. The rise of graphs is not primarily a preference for nodes and edges. It is a response to a complexity explosion. As roles, tools, states, reviews, dependencies, and rollback paths multiply, topology becomes unavoidable.

The graph's real contribution is that coordination becomes explicit.

Prompts express intent. Workflows sequence action. Loops introduce feedback. Graphs organize coordination.

Each generation repairs a weakness in the last. But graphs repair only one part of the system.

Cognition has argued that developers should avoid multi-agent architectures because they fragment context, lose information between roles, create conflicting decisions, and add coordination overhead. In many cases, a single agent with a long context is indeed more reliable. Information does not need to be repeatedly transferred, and the decision process remains more coherent.

That criticism is valid. It is also not a counterargument to the thesis here. It describes what happens when we build the graph without building the operating system around it.

Without shared state management, memory routing, permission boundaries, and arbitration, adding agents increases coordination cost and widens the surface for failure. A graph can connect roles without turning them into a reliable organization. Until the operating-system layer matures, a single agent with a long context will remain the better engineering choice for many tasks.

The problem is not that multi-agent systems are inherently wrong. The problem is that we have confused connecting agents with organizing them. A graph can tell us which roles are connected. It does not tell us who has authority, who is accountable, who may change the rules, or who resolves conflict.

2. Why Frameworks Are Not Operating Systems

A natural response is that frameworks such as LangGraph and AutoGen already provide many of these capabilities.

They do.
They let developers define nodes and edges, persist state, create checkpoints, configure retries, and insert human approval into an execution path.

The distinction is not capability. It is the distinction between mechanism and policy.

Frameworks provide mechanisms. They tell you what a system can do.

A framework may let you configure retries, but it does not decide how many failures require escalation. It may let you write memory, but it does not decide who is allowed to write, which entries require confirmation, or which projects must remain isolated. It may let you add a human interrupt, but it does not define which actions require human approval. It may let you modify the graph, but it does not determine who has the authority to alter the root mission.

This neutrality is not a flaw. It is the point of a framework. A framework must remain flexible enough to support many products, teams, and operating assumptions. If LangGraph imposed one retry policy, one memory model, or one approval hierarchy on every application, it would become less useful as a framework.

An operating system is where those choices become enforceable policy.

Frameworks give you mechanisms. An operating system is where policy lives.

A framework may expose process creation. An operating system decides who may create processes, how many resources they receive, when they are terminated, and how they are isolated. A framework may expose device access. An operating system defines permissions, boundaries, and failure handling.

Likewise, an agent framework may expose nodes, edges, checkpoints, and hooks. An Agent OS must decide who may call a tool, modify memory, restructure the graph, override a rule, or change the mission.

Frameworks are therefore not the enemy. They may become the substrate on which an Agent OS is built, much as an operating system relies on system calls, drivers, and hardware abstractions. An Agent OS could be built on top of LangGraph.

The question is not whether we should use frameworks. The question is who owns the policy layer that frameworks intentionally leave blank.

3. Why the Graph Is Still Not Enough

Graphs are necessary for complex agent systems. They are not sufficient.

First, runtime behavior already exists, but it is often scattered across local configuration rather than governed by a coherent arbitration layer. A node may retry after a timeout. A branch may roll back after failure. A task may stop when a budget is exhausted. But what happens when "maximize quality," "control cost," and "finish on time" conflict?

A collection of node-level settings cannot, by itself, determine which policy should dominate. Local rules may all be reasonable while the global system remains inconsistent.

Second, a graph can form a loop, but it cannot inherently decide when the loop should stop. A planner produces a plan. A deterministic check validates its structure. A reviewer evaluates its quality. Failure routes the task back to the planner. That is a sensible local loop.

But once the path has failed repeatedly and reached a predefined limit, another retry may no longer be recovery. It may be waste.

That is what happened in the opening example. Every revision looked reasonable in isolation. Every rejection had an explanation. Together, those locally justified decisions produced more than 30,000 unnecessary lines of code.

The root problem may not be the planner. The mission may be internally inconsistent. The reviewer may be enforcing incompatible standards. A tool may be unavailable. Context may be missing. The model may simply lack the capability required by the task.

A local loop can continue repairing local output. It does not naturally recognize that the failure sits outside the loop.

Third, we ask language models to judge far too many questions that are not linguistic. Whether output is valid JSON does not require semantic understanding. Whether code compiles does not require reflection. Whether a retry counter has crossed a threshold does not require an LLM.
File existence, token limits, schema validity, permissions, and budget constraints all have deterministic answers.

Yet many agent systems still ask a model to "check" them. A decision that could be made with near-zero latency, zero tokens, and deterministic behavior becomes slower, more expensive, and probabilistic.

Use models for ambiguity. Use code for certainty.

Fourth, a graph without persistent identity is an organization chart that forgets itself every time it restarts. It may know the dependencies of the current run, but not the user's standing preferences, the decisions already made within the project, or the failure mode encountered last week. Each execution must rediscover the user, reconstruct the project, reload its rules, and risk repeating the same mistakes.

Fifth, a graph can decompose a goal. It cannot prove that the goal is correct. A planner can translate a vague objective into subgoals. It cannot infer, from the objective alone, what reality the user ultimately wants to change or how unstated priorities should be resolved.

If the root objective remains ambiguous, the graph will simply execute ambiguity more efficiently.

A graph represents coordination. It is not the machinery that governs coordination.

4. When the Graph Stops Being Just a Diagram

The Dynamic Graph

A static graph and a dynamic graph do not need to be treated as separate systems. They are two layers of the same representation.

The topology describes responsibilities, dependencies, data flow, and control flow. Runtime metadata describes whether a node is running, waiting, blocked, retrying, failed, or complete.

Most of the time, the state changes while the topology remains stable. Nodes move from waiting to running, from running to failed or complete. Edges become active, blocked, or used for rollback.

The topology may also evolve, but modifying it is not ordinary execution. It is a privileged operation that must be governed. A system may replan, replace roles, add review nodes, or restructure a path, but it must know who is authorized to change the graph, what evidence justifies the change, and when human confirmation is required.

In this sense, an Agent OS is fundamentally a state machine. The graph describes the system's structure. State describes what that structure is becoming over time.

The human interface should therefore not be a dead flowchart. It should show a live system: active paths, blocked dependencies, rollback edges, memory injection, and failure propagation. Selecting a node should reveal its inputs, outputs, policies, provenance, and execution history.

The graph is not the operating system itself. It is the operating system's human-readable language.

Runtime

The graph says what should happen. The runtime determines how it happens.

The runtime schedules work, manages parallelism and queues, enforces timeouts, retries tasks, persists checkpoints, performs rollbacks, propagates failure, allocates resources, and controls cost. It determines when a node begins, where recovery resumes, which results can be reused, and which parallel branches must be cancelled.

Without a runtime, the graph is an execution plan. With a runtime, it becomes a running system.

The Deterministic Gate

The Deterministic Gate is one of the easiest layers to build and one of the most frequently neglected.

It handles every condition that code can evaluate precisely: schema validation, output format, compilation, type checks, tests, file existence, permissions, paths, retry counts, token limits, budgets, and fixed routing rules.

Suppose a node must emit valid JSON. Code can validate that with almost no latency, no model tokens, and deterministic output. Asking an LLM to judge the same result introduces additional cost and delay, while still allowing the model to interpret invalid structure as "mostly correct."

Or suppose output must be Markdown but must not contain a table. That does not require a reviewer's semantic judgment. The structure can be parsed directly.

The value of deterministic checks is not only efficiency.
It is the creation of non-negotiable boundaries. A hard failure should stop the path immediately. The model should not be asked whether it believes it has failed. Only questions that genuinely require interpretation should move to a reviewer, a voting mechanism, or a human.

This distinction reveals two different philosophies of agent design.

The first throws intelligence at every problem. The second designs a system.

Knowing When to Stop, and Why

When a loop repeatedly fails, the system must do two things: stop the loss and identify the cause.

Stopping the loss is comparatively straightforward. Retry limits, time limits, token limits, and budget ceilings can all be enforced by the Deterministic Gate. None of them requires understanding why the task failed. They only prevent continued waste.

If the coding agent from the opening example had been paused after crossing a code-growth threshold, budget limit, or rejection count, the 30,000-line failure would not have continued expanding. The root cause would still be unresolved, but the unresolved problem would no longer be converted into unbounded resource consumption.

Attribution is harder. Did the failure originate in the goal, the plan, the worker, the reviewer, the memory, the tool, or the interaction among them? This is a credit-assignment problem.

Having one LLM supervise another does not automatically solve it. The supervisor can also be wrong. Adding another meta-reviewer risks an infinite regress: who supervises the supervisor?

The more defensible approach today is not to grant a diagnostic role absolute authority. Such a role may generate hypotheses, compare evidence, recommend replanning, switch models, or request missing information. It should not make every high-stakes decision alone.

Countable limits belong to code. Ambiguous diagnosis belongs to models. Critical judgment escalates to humans.

That is not a failure of automation. It is an honest boundary around what the system can know.

Permissions, Tools, and Security

Once multiple agents share tools, memory, and objectives, permissions are no longer an optional enterprise feature. Who may read what? Who may modify what? Which policies are read-only? Which tool calls require approval? Which actions are irreversible? Who has veto power? Who may restructure the graph? Who may write into the Brain?

These rules determine whether the system is an organization or merely a collection of models capable of contaminating one another.

The tool layer is the device layer of an Agent OS. Browsers, Git repositories, filesystems, Stripe, and email systems resemble drivers. Each has its own permissions, sandbox, rate limits, failure modes, and external side effects.

Reading a webpage and deleting a production database should not share the same authority. Drafting an email and sending it are different operations. Creating a Stripe test object and issuing a real refund should not sit behind the same default permission.

When tools are treated as ordinary functions, the system underestimates the risk of touching the external world. When they are treated as controlled devices, permissions, approvals, and isolation become architectural.

This is also the security boundary of the Agent OS. Prompt injection is the buffer overflow of this environment: untrusted input reaches a privileged execution path. Poisoned memory is more dangerous still. It behaves like a persistent rootkit, carrying an attack across future runs.

If a browser node reads malicious instructions from a webpage and writes them into long-term memory, the attack is no longer limited to one task. It can influence other nodes, later runs, and potentially other projects.

Permissions are therefore not only governance. They are security.

The operating system begins where the graph stops being a diagram and starts becoming a governed runtime.

5. The Brain Is Not RAG. It Is How the System Persists Through Time.

Many agent systems treat memory as a retrieval step: search a vector database, insert relevant passages into the prompt, continue execution.
A Brain must do more than retrieve.

First, memory requires scope. User-level preferences, project-level rules, and reusable assets cannot be mixed together. One project using pnpm does not imply that every project must use pnpm. One brand preferring minimal interfaces does not mean every design task should inherit the same aesthetic. One user preferring English replies does not mean every team member shares that language preference.

Without scope, more memory produces more contamination.

Second, memory injection requires routing and permission. Execution nodes should not be free to search the entire Brain. Unrestricted access increases noise, token cost, leakage, and exposure to poisoned context.

A more disciplined architecture works differently. Non-overridable system rules are injected by the runtime. A lightweight router selects the preferences, project context, and assets relevant to the current task. The planner binds that context to specific nodes when generating the graph. Workers see only the information already selected and authorized for them.

An execution role should not decide for itself what it is entitled to know.

Third, memory writes require governance. A system should not convert an offhand comment into a permanent user rule. At the end of a task, it may propose a memory update, explain what it wants to store, define the scope, show the source, and identify conflicts with existing entries. The user may approve, edit, or reject it.

Every memory entry should also be traceable, reversible, and capable of expiring. When a user asks, "Where did you learn this?", the system should be able to return to the original conversation, run, and node.

Memory includes more than stable rules and knowledge. It also includes experience: an API that repeatedly failed during a run, an implementation pattern that broke in this environment, or a reviewer judgment later shown to be wrong. These experiences may not deserve promotion into permanent policy, but they should still influence future decisions.

The purpose of the Brain is not to store more. It is to know what should be remembered, where it belongs, who may use it, when it should expire, and why it exists.

Memory is not what an agent retrieves. It is what allows an operating system to remain the same system across time.

6. The Human Is Not an Approval Button. The Human Is the Source of Authority.

Human-in-the-loop is often implemented as an approval step after the agent reaches a risky action. Execution pauses, and the human clicks confirm. That is too narrow. The human's most important role is not approving a tool call, but holding Mission Authority.

A prompt should not move directly into execution because a human's first description is often incomplete, ambiguous, or internally inconsistent. "Build me an AI product that makes money" is not yet a mission. It is an intent that has not been compiled.

The first phase of the system should therefore not be planning. It should be clarification. A capable model must discuss the task with the human until it understands the reality the user wants to change, the definition of success, the failure conditions, the budget, the timeline, the risks, and the non-negotiable constraints. It must separate root objectives from temporary preferences, expose conflicts, and surface assumptions that have not yet been stated.

The output should not be a task list. It should be a Mission Specification.

But comprehension itself should be reviewed. We write unit tests, integration tests, and code reviews for software, yet frequently allow the system's first interpretation of human intent to flow directly into execution.

We test code obsessively and let comprehension go untested.

An independent model cannot create ground truth. Only the human can confirm what the human means. But an independent review can reduce correlated error. A model may remain perfectly consistent with its own misunderstanding. A second reviewer is less likely to reproduce the same mistake for the same reason.
As with code review, independence does not prove correctness. It reduces blind spots.

The review should look for missing requirements, invented assumptions, misunderstood priorities, internal contradictions, and success criteria that cannot be verified. If problems are found, the system returns to clarification. If no obvious problem remains, the human still confirms the mission.

Ground truth comes from one place: the human confirming what they actually want.

Only then should the planner decompose the mission into subgoals, generate the graph, and assign work to nodes. The system may modify execution paths, model choices, roles, retry strategies, local objectives, and even the graph topology when authorized. It may not silently rewrite the root mission.

Once the system can change the objective to make success easier, it is no longer solving the user's problem. It is redefining success.

The human is therefore not an external prompt provider and not an ordinary worker node.

The human is not merely in the loop. The human is the source of authority for the graph.

7. The Future of the Graph Is to Become the Interface to an Intelligent Operating System

Graphs will not disappear. They will become more important, but their role will change.

Today, graphs primarily represent workflows. In an Agent OS, the graph becomes an execution topology, state interface, debugging surface, permission map, memory-injection view, provenance tool, and governance console.

The human is no longer looking at an architecture diagram. They are observing a running intelligent organization.

One node is executing. Another is waiting for permission. A path has been terminated because it exhausted its budget. A tool returned untrusted content and was isolated. A memory update is waiting for confirmation because it conflicts with an existing rule. A loop has failed repeatedly, and a diagnostic role is generating possible causes. The root mission remains under human authority.

At that point, the graph is no longer merely a diagram of how agents connect. It is the language through which humans understand, observe, and intervene in the system.

An Agent Operating System can therefore be defined as:

A governed runtime that coordinates models, tools, memory, deterministic logic, and humans around a shared mission. The graph is its human-readable language.

An Agent OS is not a collection of agents. More agents only means more roles. It is not a more complicated workflow. A workflow describes an execution path. An operating system governs state, permissions, memory, failure, cost, and authority.

And the graph is not the Agent OS. It is the unified representation and control surface. The system itself depends on the runtime, the Brain, the Deterministic Gate, the tool layer, and enforceable policy.

For the past several years, the central question has been how to make an agent more intelligent: larger models, longer contexts, better tool use, stronger reflection.

But the agent that produced 30,000 lines overnight did not lack the ability to generate more code. It did not need another round of reflection. It lacked a system capable of deciding when to stop, locating the source of failure, resolving policy conflicts, preserving the right memory, and maintaining human authority over the mission.

Once intelligence expands from one model into many roles, from one response into continuous operation, and from internal reasoning into action on the external world, the problem changes.

The question is no longer only how to build a stronger agent. It is how to build an operating system in which models, tools, deterministic programs, and humans can collaborate around a shared mission, fail safely, recover, learn, and remain governable.

The history of computing is, in large part, the history of organizing complexity. We organized instructions, then programs, then processes, networks, and distributed systems.

AI is entering the stage where intelligence itself must be organized.

The operating system is already emerging in fragments.
The only question is whether we design it deliberately, or continue discovering it one patch at a time.

Graphs are not the destination. They are the language of the next operating system.

We are no longer building isolated agents. We are beginning to build operating systems for intelligence.

### 核心論點

- Loop→Graph 是必然演進但不足以解決治理問題：graph 只表達協調結構，不決定誰有權終止 loop、仲裁政策衝突、修改根目標
- Framework（LangGraph/AutoGen）提供 mechanism，OS 才提供 enforceable policy——區分「系統能做什麼」與「該怎麼做」
- Deterministic Gate：能用程式碼確定判斷的事（schema/compile/token limit/retry count）不該交給 LLM 判斷，只有真正需要語意理解的問題才升級給模型或人類——直接呼應「判斷 vs 決定」公理
- Brain（記憶）需要 scope（user/project/asset 分層隔離）、routing/permission（節點不能自由搜整個 Brain）、write governance（寫入前需提案 + 來源 + 衝突揭露，人類核可）——呼應 episodic-first 記憶治理原則
- Human 不是 approval button，而是 Mission Authority 來源：第一階段應是 clarification 產出 Mission Specification，並由獨立 reviewer 檢查理解偏差後才進入 execution，系統不得靜默改寫 root mission
