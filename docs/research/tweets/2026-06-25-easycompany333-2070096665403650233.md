## 核心摘要

> 此影片為 Anthropic engineer conference workshop 的中文字幕版（與 vmlops 版本為同一場次）：Anthropic 工程師 Andrew 與 Ash 揭示如何設計讓 Agent 自我優化運行數天的 harness 架構，核心是 Generator-Evaluator 對抗式評估迴圈。

- **Agent 長時運行三大障礙**：Context 有限（記憶重置、Context Rot、Context Sense Anxiety）、規劃能力弱、模型無法準確自我評估輸出品質
- **模型能力里程碑**：從 Sonnet 3.7（1 小時）→ Sonnet 4.5（30 小時）→ Opus 4.6（12 小時基準 / 實際可更長），模型與 harness 共同演化
- **核心架構：Planner + Generator + Evaluator 三角**：Planner 產生高階 sprint 規劃；Generator/Evaluator 在開始建構前協商「完成條件契約（Done Contract）」；Evaluator 以獨立 context window 進行對抗性評估，甚至使用 Playwright 實際操作 app
- **品味可量化**：UI 設計以 Design / Originality / Craft / Functionality 四維評分，設定強觀點的 rubric 能顯著提升輸出品質，防止 AI slop
- **Opus 4.6 帶來簡化**：原本複雜的 per-sprint 評估在 Opus 4.6 下可簡化為單 session 連續建構，server-side compaction 讓 agent 可無限運行

## 整理版（可讀逐字稿）

### 背景：Claude Code 的一年演化（00:00–01:18）

Andrew 介紹本次 workshop 是 engineer conference 首場 session。他引用 Boris（Claude Code 創始人）在一週年時的感言：一年前 Claude 還在為 bash 命令掙扎、只能跑 20 分鐘；現在幾乎所有 Claude Code 都是 Claude Code 自己寫的，且能持續數天運行。

### Agent 長時運行的三大挑戰（01:18–02:46）

**挑戰一：Context 限制**
- Context window 有限：新 session 等於失憶，必須有記憶組件
- Context Rot：越深入 session，連貫性越差
- Context Sense Anxiety：模型接近 context 上限時會緊張地匆忙收尾

**挑戰二：規劃能力不足**
- 模型傾向一次性完成所有事，或做到一半停下
- 可能建了 UI button 但 backend 完全不存在

**挑戰三：自我評估失準**
- 模型傾向告訴你想聽的話，看到半成品也可能認為「完成了」

### 兩大解法：改善模型 vs 改善 Harness（02:46–15:18）

**解法一：改善模型本身**
「meter chart」展示 agent 在最簡 scaffold 下完成 50% 任務的時間：
- Opus 3.7：約 1 小時
- Sonnet 4.5：約 30 小時（配合 Claude Code 2.0 checkpoints）
- Opus 4.6：約 12 小時基準（實際已實現更長）

**解法二：改善 Harness**
Anthropic Agent SDK 提供核心原語：agent loop、MCP server、sub-agent 委派、Claude.md/skills/slash commands、權限系統。

技術里程碑回顧：
- **Computer Use**：能截圖、點擊、自測程式碼
- **Claude Code（Feb 2025）**：Sonnet 3.7，最初定位為實驗性工具
- **Ralph Loop**：「可預測失敗優於不可預測成功」——planning phase → 拆分 features → 各開新 session 工作
- **Claude Code 2.0**：Checkpoints + context-aware tracking
- **Haiku 4.5 完成家族**：sub-agent 在經濟上可行，開始大規模使用
- **Sonnet 4.6 + Opus 4.6**：Opus 4.6 定義為最強 agentic 模型；Agent Teams（sub-agent 互通）；Server-side Compaction（無限運行）；1M context GA

### Ash 接棒：Generator-Evaluator 對抗式 Harness（15:18–36:38）

**為什麼不能自我評估？**

就像批評一道菜比自己烹飪容易——訓練一個「嚴格的 standalone critic」比要求 builder 自我批評有效得多。

**品味量化**：
Anthropic 的四維評分 rubric（Design / Originality / Craft / Functionality），使用者可根據模型特性調整權重（Opus 4.6 功能性已強，更強調 Design + Originality）。用參考網站校準評估器的品味，防止 AI slop。

GAN 式 harness 的關鍵優勢：當 Generator 在某維度持續低分（如 originality），harness 直接丟棄重來——這是 single agent loop 或 Ralph Loop 做不到的。

**Planner + Generator + Evaluator 完整架構**：

1. **Planner**：一行提示 → 高階 sprint 清單（刻意不細化技術，避免早期錯誤沿 sprint 級聯放大）
2. **Done Contract 協商**：Generator 建構前，Generator 提出測試方案，Evaluator 可能回推「scope 太大、測試太弱」，雙方協商出明確完成條件
3. **Generator 建構**：Evaluator 對照 Done Contract 評分，而非原始 spec
4. **Playwright 實際測試**：只有真正使用 app 才能發現的 bug（如 button 有 UI 但 backend 不存在）

**真實案例：Retro Game Maker**
- 單行提示：「build a retro game maker」
- Harness 自動加入 AI assistant 功能（Planner 從 spec 中的「some AI features」推導）
- Evaluator 測試出的問題（如「音符播放但遊戲還在跑」「沒有 undo 功能」）只有使用 app 才能發現

**DAW（數位音訊工作站）案例**：Agent 設定節拍、鋪設旋律、建構鼓軌。Claude 無法「聽到」音樂，所以音樂本身很差，但 app 本身完成度很高，是 Opus 4.6 以前根本無法完成的任務。

### Opus 4.6 帶來的架構簡化（28:00–36:38）

原本複雜的設計（每 sprint 都跑 evaluator）在 Opus 4.6 下可以大幅簡化：

- 模型能在 2 小時連續 build 中保持連貫性
- 不再需要強制 per-sprint 評估
- 一個連續 session 足以處理很長的建構任務
- 成本也因簡化而下降約一半

核心 takeaway：harness 不會消失，而是隨模型能力演化——找到模型弱點、用 harness 填補、訓練模型吸收這個能力、再移除。

### Q&A 精華（36:38–01:07:44）

**評估器 rubric 是 per-project 還是可重用？** 目標是可重用——找出跨模型的共通弱點。

**Context smart zone / Ralph Loop 還有意義嗎？** Andrew 和 Ash 認為這是暫時問題；Opus 4.6 已能在更長 context 保持連貫，server-side compaction 接近解決 context rot。

**Human in the loop**：最理想是完全自主；若需要人工介入，Hooks 是最自然的原語（stop condition → 交回人類 → 繼續 loop）。另一模式：跑 10 個平行版本，人工從成功的版本中挑選。

**讀 traces 的方法**：不只是看 raw output，而是「把自己放進模型的視角」——像閉著眼睛瀏覽網頁、每 10 秒只能看一張靜態截圖。只有這樣才能真正理解為什麼模型做了某個決定，並調整下次的指令。

**Brownfield vs Greenfield**：這個 harness 模式目前最適合 greenfield 新應用；brownfield 需要更多控制，但整個軟體開發生命週期（monitoring → issue generation → PR → review）都有應用空間。
