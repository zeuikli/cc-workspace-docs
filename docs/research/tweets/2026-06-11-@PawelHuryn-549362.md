## 全文

Fable 5 is the first model that made me feel audited. 36 hours of testing and 6 experiments since it dropped.
---
Yesterday, mid-task, it read my CLAUDE.md and caught it teaching the exact pattern my own quality gate bans. I hadn't asked for a review. It hit the contradiction and flagged it on its own.

That file is 320 lines. The knowledge layer behind it is 166 files, around 300k words of rules my agents follow every day. Every one of those rules was written by and for a weaker model.

This guide is what I did about that, plus everything else from six experiments (effort dial, speed head-to-head, time-to-first-token, depth chain, recursive workflows, nesting cost).
Every experiment here I ran myself (scripts, logs, data: https://github.com/phuryn/experiments/)
---
## 1. The First Prompt I'd Run
Before you give Fable 5 real work, give it this:
```markdown
Read your own instruction files (CLAUDE.md, skills, rules, memory files) end to end.

1. Where do they contradict each other? Quote both sides.
2. Which rules exist to manage a weaker model: guardrails for failure
   modes you don't have, recipes for things you no longer need spelled
   out, hardcoded facts that have drifted? List them with file:line.
3. Which rules teach by bad example: documents that violate the
   patterns they prescribe?
4. What would you delete? What would you keep exactly as is, and why?

Don't fix anything yet. Report first. I decide what gets cut.
```
The audit goes first for a structural reason. A knowledge layer that agents help maintain has a blind spot: every rule an agent added passed review by the model that added it. The errors that survive are the ones that model couldn't see. A system maintained by model N preserves the errors model N can't see, and they sit there until a stronger reader shows up. Right now that reader is Fable 5.

## 2. What Fable Found in My Repo
My agents maintain those files, not me. I trusted Opus to keep them clean. Five finds from one audit:
- A hardcoded date telling the model what day it is: "(today is 2026-05-24)", written in a May session, never noticed again. It fed the wrong date into every session that loaded it.
- A rule documented with the pattern it bans. My writing system bans em dashes in published content. The file documenting the ban is written with em dashes. Instructions teach by example as much as by rule.
- My CLAUDE.md taught a drafting pattern my own quality gate is built to catch.
- Guardrails for failure modes the new model doesn't have: a follower-count threshold that drifted (50K when the rule was written, 75K now), "never delegate judgment-heavy work to cheaper models," double-check rituals priced for an older lineup.
- The same rule stated in three files. Three chances to drift apart.
Some of these a careful grep would catch. The ones that matter wouldn't: rules that were right for the model they were written for, wrong in meaning rather than in syntax. No automated check finds those. That's the trap. The better your system was for the last model, the more it holds back this one.
This isn't only my read. The Claude Code team describes the same behavior from the other side: Boris Cherny asked Fable to debug something and it took measurements, added logs, and verified the fix before declaring done, with nothing in the prompt telling it to.
The model does the reading. You do the deleting.

## 4. What I Measured After the Audit
The table is what changed on paper. What actually changes how you use the model isn't on a spec sheet, so I measured the two settings that do: effort and speed. Five rounds each, stream-level timestamps, exact token counts.
[圖 2]
The effort dial barely matters until you force it. Below max the dial moves little: thinking is adaptive, and the model ignores budget it doesn't need. Max doubles or triples the time and swings between runs.
On a hard math puzzle with a checkable answer, every effort level got it right with the same method. The extra seconds bought re-verification and caveats, not a different answer.
Based on my experiments so far: Default to high. Max is the re-verification tax.
Next finding, the "Fable is slow" complaint that flooded X is half true.
[圖 3]
It starts later: first visible activity came at 7.4 to 8.2 seconds versus Opus at 4.7 to 5.3, no overlap, and that blank pause, ~3 seconds, is where the "it crawls" feeling comes from. But once moving it's denser, not slower.
Same math problem, both models correct: Fable used about 40% fewer output tokens and finished 5 to 9 seconds sooner. And on a heavier multi-file audit the gap vanished, 59 seconds against 63, while Fable caught a third more issues. Budget a little patience at the start of an exchange. Stop worrying about the rest.
Don't trust the docs, don't trust the discourse, run it and read the numbers. Same move as the audit, pointed at the model instead of your files.

## 5. The Safeguard Layer Most Coverage Missed
Fable 5 is the general-access version of a stronger model Anthropic doesn't fully release: Mythos 5, limited to trusted partners. Same model, classifier-gated. That gating is the safeguard layer, and it's the part most launch coverage skipped.
[圖 4]
Fable 5 ships with classifiers that screen for high-risk domains. Trip one and the session routes to Opus 4.8 instead, with a notification. Anthropic puts it at ~5% of sessions. It doesn't fail the query. It hands it to a different model, on purpose, and tells you.
[圖 5 — 來源: My own experiments with subagents got capped, too]
The capability ceiling and the safeguard layer are different things, and knowing which one you hit changes what you do next. The classifiers are trigger-happy and Anthropic says so (Cherny: "We know the classifiers are trigger-happy, and are working on improving it"). If your work touches security, healthcare, or biotech, expect occasional routing. The notification is your signal: you did nothing wrong, and the floor is "merely Opus 4.8."
There's a second layer almost nobody read. Per the system card, Section 1.5, requests targeting frontier AI development don't reroute. They get quietly degraded, no notification, on ~0.03% of traffic. Unless your team pretrains models, you're unlikely to hit it. Still, the model you bought can be tuned down by topic, silently.
One more thing for teams: when per-token access opens June 22, the API has no automatic fallback by default. A tripped classifier blocks the request and returns a refusal category. Server-side fallback to Opus is opt-in.

## 6. How Deep Do Agents Stack Now
The launch shipped a quieter change: nested subagents. Cherny: "Just landed nested subagent support in Claude Code... Capped at depth=5 to start." Agents kicking off agents to manage context.
I spent the morning testing where that cap actually lives:
[圖 6]
- Cherny puts the cap at depth=5. What I actually hit: the spawn tool was already gone at depth 1 in Claude Code web and 7 on Desktop. My subagents reported "Agent tool present: no." The rollout is staged, so the depth you get moves with the surface and the week. Check the toolbox before you design around a number.
- The cap doesn't exist outside the Task tool. A Claude session can run claude in its own terminal. I chained six levels deep that way, around 30 to 45 seconds end to end, with no resistance at any level. The only limit was the one I set in the script.
- Depth is multiplicative, not free. I ran nested-vs-flat twice on CLI-composed workflows: a toy task (1.84x cost, the middle managers ate 71% of the budget while producing none of the analysis) and a real workload over four months of my own post data (1.63x, the managers' share fell to 32% as the leaves did real work). The overhead shrinks as the leaves do real work. A coordination layer still pays a full session's overhead to run.
The decision rule: nest when the next level's plan depends on what the previous level found, or when a branch needs its own clean context. A flat fan-out at depth 2 beats an org chart at depth 5 for almost everything. The cap is the platform's. The budget is yours.
This is the same migration as the audit, one layer down. Your delegation rules were written for a world where agents couldn't spawn agents. "One agent or a team of agents" is now an architecture decision with an invoice attached, and the answer is the same as for human orgs: add a management layer only when coordination beats direct work, because a manager costs the same whether or not it earns its keep.

## 研究摘要

**TL;DR**：Fable 5 第一個 prompt 應該是讓它審計你的 CLAUDE.md；effort 預設 high 即可；flat fan-out 幾乎總是比 nested org chart 便宜（1.63-1.84×）。

### 核心論點

1. **Instruction file audit as Day 0 prompt**：Fable 5 能找出「為舊模型寫的過時守衛」——這類錯誤在 syntax 上是對的，但 meaning 層面已過時；grep 找不到，只有更強的模型讀後才能察覺
2. **Migration gotchas（立即可避）**：`thinking: disabled` → 400；temperature 參數消失；API 到 6/22 前無法存取
3. **Effort dial 實測**：adaptive thinking 讓 dial 在 max 以下影響小；max 只買到重複驗證，不買更好的答案 → default high 是最佳 cost/result
4. **Speed 真相**：啟動慢（+3s time-to-first-token），但輸出密度更高——同問題少 40% output tokens、完成快 5-9 秒；重任務下差異消失（59s vs 63s，但多找 1/3 問題）
5. **Nested subagents 成本實測**：depth 是乘法不是免費——toy task 1.84×（manager 吃 71% budget 卻不產出分析）；real workload 1.63×（manager 降至 32%）→ nest only when plan depends on prior level or needs clean context

### 關鍵數據 / 工具

- Time-to-first-token：Fable 7.4-8.2s vs Opus 4.7-5.3s（+3s 空白感）
- Output token 效率：同 math problem，Fable 少 40% output tokens，快 5-9s
- Multi-file audit：Fable 59s vs Opus 63s，但多捕捉 1/3 問題
- Safety classifier：~5% sessions route 到 Opus 4.8（有通知）；Section 1.5 quiet degradation ~0.03%（無通知）
- Nested cost：toy task 1.84×（manager 71%）；real workload 1.63×（manager 32%）
- Recursive dynamic workflows：L2 to L6 in 107 seconds
- Data：github.com/phuryn/experiments/
- Audit prompt 模板：4 問題結構（contradictions / legacy guardrails / bad examples / deletion list）

### 批判性觀察

1. **深度實驗內容在付費 newsletter 後方**：migration workflow 的三桶分類、/goal patterns、recursive workflows 細節全在付費牆後；這篇 article 是廣告文，影響完整度
2. **Effort dial 實驗樣本（5 rounds）偏小**：「max 不買更好答案」的結論基於單一 math puzzle，泛化性需謹慎；complex 開放性任務的結論可能不同
3. **Nested cost 數字最具價值**：1.63-1.84× 的具體倍數是目前社群中最量化的 overhead 數字，可直接用於 architecture decision
