## 核心摘要

### Part 1：Boris Cherny — Claude Code 誕生故事

> Boris Cherny 首度深度回顧 Claude Code 從「兩天原型」到 Anthropic 最重要產品的完整歷程，分享 CLAUDE.md 哲學、Loops 範式、以及他對 AI 時代工程師技能的全新看法。

**Claude Code 是意外**
- 第一個原型做完兩天後，Boris 就把它給團隊 dogfooding
- 同事 Robert 直接在電腦上用，Boris 嚇了一跳：「這還沒準備好啊！」
- 內部口耳相傳，Dario 看到使用曲線幾乎垂直上升，問「你在強迫工程師用嗎？」答：「沒有，他們自己找到的」
- 從 CLI 起步是因為「最便宜的做法」，後來就一直留在 CLI

**早期使用模式（2024 年）**
- 最初：自動化 git 指令、bash 操作、Kubernetes 管理
- 首個高採用率功能：寫 unit tests（風險低，模型還差但夠用）
- 工程師自發幫自己寫 markdown 說明檔 → 這就是 CLAUDE.md 的起源

**CLAUDE.md 哲學：「等待需求」（Wait for Demand）**
- Boris 個人的 CLAUDE.md 只有兩行：
  1. 每次開 PR 自動 enable auto merge
  2. 每次開 PR 貼到團隊 Slack channel 求 stamp
- 其他指令都在 codebase 裡共享的 CLAUDE.md
- 核心原則：不事先設計 UI，因為六個月後模型已完全不同，所有 scaffolding 都會過時

**不要為模型加 scaffolding**
- 加 scaffolding 最多提升 10–20% 效能，但下一個模型發布後就歸零
- 要麼：每次模型更新後重建 → 要麼：等下一個模型，免費得到那 20%
- 這是 Claude Code 一直留在 CLI 的根本原因

**記憶體洩漏 vs. 重新學習**
- Boris 花時間手動 heap dump 分析記憶體洩漏，結果另一位工程師 Chris 直接請 Claude Code 分析
- Claude Code 自己寫了分析工具，找漏洞比 Boris 快
- Boris：「我必須一次又一次重新學習這個教訓——我的腦子還停在六個月前」

**根據 Claude Code transcript 招募工程師**
- 有公司已開始要求應聘者上傳一段用 Claude Code / Codex 解決 feature 的錄影
- Boris 認為可行：可以看出對方是否看 log、能否在 agent 跑偏時糾正、會不會用 plan mode
- 理想的「蜘蛛網圖」技能評分：systems 思考、testing、user behavior、設計感

**CLAUDE.md 的 TypeScript 類比**
- TypeScript 不是學術設計，是從觀察 JavaScript 程序員如何寫程式倒推出來的
- Claude Code 也是：Boris 為自己打造工具，然後為團隊，然後為 Anthropic 員工，然後為用戶
- 結果：實用但不學術 ≈ TypeScript vs Haskell

**Claude Code terminal 是 React 應用**
- Boris 用 React 打造終端機介面，因為他是前端/設計混合型工程師
- 在 80×100 字元、256 色、單一字體的限制下設計 UI 極具挑戰

### Part 2：AI Second Brain — 五個層次架構

> 另一創作者的 Claude Code 知識管理教學，用 Markdown 檔案組織個人/團隊知識庫。

**核心理念**
- 「你的模型就是你的資料，你的 IP」
- 問題不是有沒有資料，而是 agent 能不能在對的地方找到它

**五個層次**
| 層次 | 特徵 | 適用情境 |
|------|------|---------|
| Level 1 | 手動資料夾結構，靠精確關鍵字搜尋 | 入門，<30 個筆記 |
| Level 2 | LLM Wiki，帶關係圖（Obsidian 視覺化） | 30+ 筆記，需要概念關聯 |
| Level 3 | 語意搜尋，不靠精確字詞 | 路由失效，需要模糊查詢 |
| Level 4 | 知識圖譜，追蹤問題鏈 | 複雜關係推理 |
| Level 5 | 多 Agent 離線同步（如 G-brain） | 大型團隊資料同步 |

**關鍵設計原則**
- 反向工程：先想「未來怎麼用這個資料」再決定怎麼存
- 「籃球框和籃球」：知道資料怎麼被取用，才能決定存放格式
- 整個專案不需要只在一個層次：某資料夾 Level 2，另一個 Level 4 完全合理

**工具提及**
- Obsidian（視覺化 Markdown 關係）
- GitIngest（GitHub repo → 單一文字）
- DeepWiki（自動為 repo 生成 docs）
- Hermes agent、Codex（second brain 與多模型兼容）
