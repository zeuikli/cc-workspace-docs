- RLHF：以人類偏好資料（規模達 1M 筆）訓練獎勵模型後再強化學習；人類標注員自身一致率僅約 66%，LLM-as-judge 在成本與一致性上均優於人類標注

## Part 1 整理版（Building LLMs — 01:44:17）

### 1. 什麼是 LLM（00:00–08:00）

講師以 ChatGPT、Claude、Gemini、Llama 等為例介紹大語言模型（Large Language Models）。今天課程的目標是一個概覽：從架構、資料、評估到對齊，走完整個訓練管線。

核心定義：LLM 是**自迴歸語言模型**（autoregressive language model）。做的事情非常單純——給定一段文字，預測下一個 token 的機率分佈。所有的「聊天」「推理」「coding」能力，都是這一個簡單目標訓練出來的湧現結果。

### 2. 架構基礎：Transformer（08:00–21:00）

自迴歸 LLM 的計算流程：
1. **Tokenization**：將文字切成 tokens（通常是 subword 單位，如 BPE）
2. **Embedding**：每個 token → 向量表徵（embedding vector）
3. **Transformer Layers**：多層 self-attention + FFN，對整個 context 產生聯合表徵
4. **Linear + Softmax**：投影到 vocabulary size 維度，得到下一 token 的機率分佈

Vocabulary size（詞彙表大小）同時也是模型最後一層的輸出維度，通常在 32K–128K 之間。Tokenization 設計對模型表現影響顯著，不同 tokenizer 會導致 perplexity 不可比較。

### 3. 評估指標與 Benchmark（21:00–39:00）

**Perplexity**：訓練過程最核心的指標，等同於模型對「下一 token」的驚訝程度。數字越低越好。現在已不用於學術排名（因為依賴 tokenizer 與測試集選擇），但訓練期間仍是最重要的開發信號。

**主流 Benchmark**：
- **HELM**（Stanford）：涵蓋問答、摘要、毒性偵測等多個維度
- **MMLU**（Massive Multitask Language Understanding）：覆蓋大學物理、醫學、天文等 57 個知識領域的選擇題，是最常用的能力評估
- **HuggingFace Open LLM Leaderboard**：開源模型的公開排行榜

評估方式：給模型四個選項（A/B/C/D），比較各選項的生成機率或讓模型直接輸出字母。

### 4. 訓練資料與規模法則（39:00–55:00）

**訓練資料演進**：
- 早期（學術規模）：~150B tokens，約 800 GB
- 當前主流：~15T tokens，~100 TB

主要來源：Common Crawl（網頁爬取，須大量過濾）、arXiv、PubMed、Wikipedia、GitHub、Stack Exchange、書籍等。「The Pile」是代表性的學術開源資料集，揭示了典型的資料分佈比例。

**Chinchilla 規模法則**（Hoffmann et al.）：在固定 compute budget 下，模型參數量與訓練 token 數應維持約 **1:20** 的比例——這讓業界從「瘋狂堆參數」轉向「加大資料量」的策略。

**Bitter Lesson**（Richard Sutton, 2019）：AI 歷史一再表明，長期贏家總是擴展計算力，而非精心設計人工 inductive bias。

**推理成本考量**：若把推理成本納入，每個 token 的參數比應提高到約 1:150（更小的模型，更多的資料），因為小模型長期運行成本更低。

### 5. 訓練成本與碳排放（55:00–01:02:00）

以訓練一個 LLaMA 規模模型為例的成本估算：
- **GPU 費用**：H100 租用約 $2/小時，訓練需 ~2,600 萬 GPU 小時 → ~$52M
- **人力費用**：50 位工程師 × $500K/年 → $25M
- **總計**：約 **$75M**

**碳排放**：約 4,000 噸 CO₂ 當量，相當於 2,000 趟 JFK↔London 來回機票——不可忽視，但在業界尚不是決策首要考量。

### 6. 對齊與微調：SFT（01:02:00–01:15:00）

**為何 Pre-training 不夠用**：預訓練模型學的是「預測網路上的文字」，但網路上的文字不是「問答」，也不包含「禁止有害輸出」的行為。SFT 就是用來解決這個落差。

**Supervised Fine-Tuning（SFT）**：在少量（5K–50K 筆）人工標注的 (instruction, response) 對上微調。模型已有語言能力，只需學習「回答問題」的格式與「遵守安全規則」的行為。

**Alpaca 案例**（Stanford, 2023）：用 175 筆人工 Q&A 加上 GPT-3（text-davinci-003），讓它生成 52,000 筆指令資料，再微調 LLaMA-7B。結果得到一個指令跟隨能力顯著改善的 Alpaca-7B，且成本極低。這示範了「LLM 生成合成資料用於 SFT」的可行性。

合成資料的風險：若反覆用同一分佈的 LLM 生成資料，模型會過擬合到生成分佈，而非學到更廣的能力（model collapse 問題）。

### 7. RLHF 與 LLM-as-Judge（01:25:00–01:44:17）

**RLHF 的動機**：SFT 訓練的是「模仿最佳答案」，但很多情況下很難定義什麼是「最佳答案」。人類偏好（哪個回答更好？）比絕對標注更容易收集。

**人類標注的挑戰**：
- 標注員自身一致率僅約 **66%**（二元選擇題）
- 收集成本高（Mechanical Turk 約 $300/千筆）
- 標注員分佈偏差（annotator distribution shift）
- 勞動倫理問題（標注員需接觸大量有毒內容）

**LLM-as-Judge**：用最強的現有 LLM 替代人類標注。實驗顯示，頂尖 LLM 的偏好一致性可超過人類（>66%），且成本大幅降低。現在業界普遍採用「人類 + LLM 混合標注」的方式。

**LoRA vs 全量微調**：業界 SFT/RLHF 通常更新全部權重；開源社群常用 LoRA（僅為每層添加低秩矩陣差值），以減少計算/記憶體成本，但表達能力有所犧牲。

## Part 2 整理版（Claude Code 實用心法 — 27:15）

> 主講：Boris（Claude Code 創作者，Anthropic MTS）

### 1. Claude Code 是什麼（00:00–04:50）

Claude Code 不是「行補全工具」。過去兩代 AI 助手（GitHub Copilot 等）設計目標是補全幾行程式碼，Claude Code 的目標是**完全自主代理（fully agentic）**：

- 建立整個功能（features）
- 撰寫完整函式、完整檔案
- 同時修復整個 bug 並理解影響範圍

Claude Code 不依賴 IDE 索引——啟動即可用，無需等待 indexing。

### 2. Codebase Q&A（04:50–11:00）

**最有效的起手式**：用 Claude Code 問問題，而不是直接要它做事。

範例：
- 「為什麼這個函式有 15 個參數？那些奇怪的參數名是怎麼來的？」
- 「這個 class 最初是什麼時候引入的，為什麼？」

Claude Code 可以翻閱 git 歷史、閱讀 commit message、追蹤 PR，提供有脈絡的解釋——這是過去要花一週讀文件才能理解的知識。

**語音輸入技巧**：macOS 的系統級 Dictation 功能可以對 Claude Code 說話，特別適合在「講英文比打字更快」的情況下輸入長段描述。

### 3. 工具 + 迭代迴路（11:00–17:00）

Claude Code 最強大的使用方式：**給它一個能驗證自身工作的工具**。

- **Unit tests**：讓 Claude Code 自己跑測試、看結果、迭代修復
- **Puppeteer MCP**：Web UI 截圖後讓它看圖自動修正樣式
- **iOS Simulator 截圖**：App UI 迭代

操作建議：
1. 如果你確定 Claude 走在正確的路上，按 `Shift+Tab` 進入 **auto-accept 模式**（編輯自動接受，bash 指令仍需手動確認）
2. 給 Claude 明確的工作流程指示：想要它直接動手還是先規劃、先確認？

### 4. CLAUDE.md 與記憶管理（17:00–18:30）

**CLAUDE.md 的角色**：Claude Code 的「永久記憶」——自動載入到每個 session 的 context 前綴。

放什麼進去：
- 常用 bash 指令（test runner、build 指令）
- MCP 工具說明
- 重要架構決策
- 關鍵檔案路徑

**建議**：CLAUDE.md 要 check in 進 git，與整個團隊共享——一人維護，全員受益。

**`/memory` 指令**：查看目前所有載入的 memory 檔案來源（enterprise policy、user 個人設定、project CLAUDE.md、nested 目錄 CLAUDE.md）；`#` 語法可立即記錄到指定 memory 檔案。

### 5. 快捷鍵備忘（18:30–19:30）

| 按鍵 | 功能 |
|------|------|
| `Shift+Tab` | 切換 auto-accept 模式（自動接受所有編輯） |

Terminal UI 的限制使得這些快捷鍵不易被發現，Boris 建議定期翻閱文件。

### 6. 企業功能與共享配置（19:30–26:00）

**Enterprise Policy 檔**：
- 可全公司統一設定「哪些 bash 指令自動允許」（無需每次確認）
- 可封鎖特定 URL 永遠不被 fetch
- 可預先配置 MCP server 清單，員工第一次執行時自動提示安裝

**Puppeteer MCP 實例**：Anthropic 內部 apps repo 的 `.mcp.json` 預先配置 Puppeteer，所有工程師在該 repo 跑 Claude Code 時自動能用截圖迭代 UI，無需手動安裝。

### 7. Q&A 精選（26:00–27:15）

**Q：Claude Code 是否支援多模態（圖片）？**
A：完全支援。可以拖拉圖片進 terminal，或從剪貼板貼上。Boris 常用方式：把設計稿截圖拖進去，說「implement this」，同時開 dev server 讓它截圖自動對比。

**Q：為什麼做 CLI 而非 IDE？**
A：兩個原因：① Anthropic 內部工程師用很多種 IDE（VS Code、Zed、Xcode、VIM、EMACS），terminal 是最大公約數；② 模型進步如此之快，Boris 預期年底前 IDE 的作用可能大幅改變，不想過度投資在 UI 抽象層上。
