## 全文

Most people use Claude Code like a smarter autocomplete.

They start a new session, explain the repo again, ask for a patch, lose context, then repeat it tomorrow.

The fix is not a longer prompt.

Your project needs a small operating system: a few files that tell the AI what it is building, how it works, and how to prove a change is safe.

Set this up once. Every future session gets better.

---

# The structure

```plaintext
your-project/
├── CLAUDE.md
├── docs/
│   ├── product.md
│   ├── architecture.md
│   └── decisions.md
├── tasks/
│   └── current.md
├── scripts/
│   └── verify.sh
└── .claude/
    └── skills/
```

Just six files. No huge framework. No 200-page wiki.

---

# 1. CLAUDE.md is the front door

Claude Code loads project memory from CLAUDE.md.

This is where you put the rules that should apply every time: stack, commands, conventions, and things the AI must never touch.

```plaintext
# Project

## Stack
- Next.js, TypeScript, Postgres
- Package manager: pnpm

## Commands
- Run locally: pnpm dev
- Test: pnpm test
- Type check: pnpm typecheck

## Rules
- Reuse existing components before creating new ones
- Never change the database schema without a migration
- Add tests for bug fixes
- Do not edit files in /legacy without asking first
```

Keep it short. Claude needs rules, not your company autobiography.

Official guide:
https://docs.anthropic.com/en/docs/claude-code/memory

---

# 2. product.md tells it what matters

Code explains how something works.

It rarely explains why it exists.

Write down the user, the job they are trying to do, and what the product should not become.

```plaintext
# Product

## User
Independent designers who send proposals to clients.

## Core job
Create, send, and track proposals without chasing spreadsheets.

## Non-goals
- We are not a full CRM
- We do not manage invoices
- We optimize for speed, not endless customization
```

This stops Claude from shipping technically correct features that pull the product in the wrong direction.

---

# 3. architecture.md prevents random rewrites

This is the map of the repo.

Explain the important boundaries: where the API lives, where data flows, which services own what, and which folders are dangerous.

```plaintext
# Architecture

- /app: UI and routes
- /lib: shared business logic
- /db: schema and queries
- /api: external integrations

## Data flow
UI -> API route -> service -> database

## Important rule
Business logic belongs in /lib, not inside route handlers.
```

You do not need to document every file.

Document the decisions a new engineer would otherwise learn the hard way.

---

# 4. decisions.md saves the expensive context

Every project accumulates weird choices.

Why did we use this provider? Why is this function ugly? Why can't we "just switch" a library?

Write down decisions once, so Claude does not reopen them every session.

```plaintext
# Decisions

## 2026-07-25: Keep Stripe Checkout
We tested embedded payments, but Checkout had fewer edge cases
and works better on mobile.

## 2026-07-12: Use server-side search
Client-side filtering became slow after 10k records.
```

Only log decisions that will matter later.

Do not turn this into a diary.

---

# 5. current.md gives Claude one job

AI agents get worse when every task feels equally important.

Before a session, write the current goal, constraints, and definition of done.

```plaintext
# Current task

## Goal
Add CSV export for proposal data.

## Constraints
- Must work for 50k rows
- No new paid service
- Keep existing permissions

## Done when
- Export works from the dashboard
- Dates are formatted correctly
- Tests pass
```

Now Claude has a target instead of a vague request like "add export."

---

# 6. verify.sh is the part most people skip

The agent should not decide that its own work is correct.

Give it a repeatable verification command.

```plaintext
#!/usr/bin/env bash

pnpm lint
pnpm typecheck
pnpm test
```

For bigger projects, add end-to-end tests, build checks, or a staging deploy preview.

The point is simple:

Claude can write the patch.

Your system needs to decide whether the patch passes.

---

# Add skills for repeated work

A skill is a reusable instruction set for a specific job.

Instead of re-explaining how your team writes release notes, reviews pull requests, generates PDFs, or tests a web app, put the workflow in a SKILL.md.

```plaintext
---
name: bug-fix
description: Use when fixing a reproducible bug.
---

1. Reproduce the bug before changing code.
2. Find the smallest responsible surface.
3. Add a regression test.
4. Run the verification script.
5. Update decisions.md only if the fix changes an architectural choice.
```

Anthropic's official skills repository includes examples for document creation, web testing, MCP building, brand guidelines, and more:
https://github.com/anthropics/skills

Skills docs:
https://docs.anthropic.com/en/docs/claude-code/skills

---

# The workflow

Once the files exist, start important tasks with this:

```plaintext
Read CLAUDE.md, docs/product.md, docs/architecture.md,
docs/decisions.md, and tasks/current.md.

Before changing code, explain the plan and the test you will run.

After the change, run scripts/verify.sh.

Only update decisions.md if we made a decision that will matter
for future work.
```

That's it.

You are no longer hiring a new AI every morning.

You are giving the same system a project brief, a map, a task, and a way to check its own work.

Most people will keep asking Claude for snippets.

The useful setup is the one that lets it understand the project before it touches the code.

## 研究摘要

**TL;DR**：入門級 Claude Code 專案架構——CLAUDE.md（規則）+ product.md（產品目的）+ architecture.md（架構地圖）+ decisions.md（決策紀錄）+ current.md（當前任務）+ verify.sh（機械驗證），加上 SKILL.md 承載可重複工作流。

### 核心論點

- 六個檔案分工：CLAUDE.md 是常駐規則（stack/commands/rules），product.md 說明「為什麼」（使用者/核心任務/non-goals），architecture.md 是倉庫地圖（邊界與危險資料夾），decisions.md 記錄「為什麼做這個選擇」避免每次重新討論，current.md 給單一明確任務目標與 Done-when，verify.sh 提供機械驗證命令（不讓 agent 自己判定成功）
- 核心原則：「agent 不該自己決定自己的工作是對的」，須有可重複執行的驗證命令
- Skill 化重複工作：把「怎麼寫 release notes」「怎麼 review PR」等重複流程寫成 SKILL.md，附範例格式
- 建議的 session 起手式 prompt：讀五個檔案 → 動手前先講計畫與測試方式 → 改完跑 verify.sh → 只在決策真的重要時更新 decisions.md

### 關鍵數據 / 工具

- 引用官方文件連結：`docs.anthropic.com/.../claude-code/memory`、`docs.anthropic.com/.../claude-code/skills`、`github.com/anthropics/skills`
- 無實驗數據，純架構模板文章

### 批判性觀察

- 本文的六檔案架構（CLAUDE.md/product/architecture/decisions/current/verify.sh + skills）是本 workspace 現有 `.claude/rules/*.md` + `.claude/refs/*.md` + `.claude/skills/*` + `memory/MEMORY.md` + `memory/LESSONS.md` 架構的**簡化早期版本**，本 workspace 已實作更成熟的四階層設計（auto-load rules / path-scoped / skills RESOLVER / memory episodic-first），本文對本 workspace 無新增資訊
- 「verify.sh 機械驗證」「agent 不自證成功」核心原則與本 workspace `core.md §TEST`（`unverified_success` 閘門、oracle 資格）方向一致但層次淺得多，僅提供 lint/typecheck/test 三行範例，無涉 oracle 資格檢驗、reward hacking 防線等進階內容
- 定位為給尚未建立任何專案結構的初學者的入門教學，適合作為對外分享的簡明範本，但對已有成熟 harness 的 workspace 邊際價值低
