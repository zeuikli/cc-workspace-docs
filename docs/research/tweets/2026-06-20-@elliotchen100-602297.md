## 全文

受到 Nate 这个视频启发：
https://www.youtube.com/watch?v=EuzYhzB0vbI
过去两天，Agent Loops 这个词出现得很频繁。大家大概能理解它不是普通 prompt，也不是单纯多开几个 agent，但真正落到工作流里，很多人还是会卡在一个问题：它到底适合干什么？
我重新看了一遍 Nate 这个视频，也结合这两天自己的体验，感觉现在最值得讨论的不是“Agent Loop 的定义”，而是哪些场景已经足够可用。
> 我理解 Nate 的核心意思是：loop engineering 本质上是把“人不断 prompt agent”这件事，替换成一个系统自己去 prompt agent。一个 loop 至少要有目标、动作、停止条件。更准确地说，是 reason、act、observe，然后重复，直到验证通过。
这里最关键的不是 repeat，而是 observe。因为如果没有验证，loop 只是更贵、更长时间的瞎忙。agent 会不停产出，但不知道什么时候该停，也不知道每一轮是不是真的变好了。
看完 Nate 提到的几个例子，我觉得目前最高可用的场景大概是下面这几类。
—
## 1. 调研到产物的循环
Nate 自己做这个视频时，就让 agent loop 去读很多来源：文章、YouTube transcript、X post 等，然后围绕 Agent Loops 这个主题不断整理，最后生成一个 HTML 页面。
这个场景很适合 loop，因为它不是一次性总结，而是“收集资料 → 形成结构 → 生成产物 → 检查遗漏 → 再补资料 → 再改结构”。
这类任务对知识工作者很实用。比如研究一个新产品、拆一个技术趋势、做一份竞品分析、整理一个课程大纲。人最烦的不是第一版总结，而是反复补洞：还有哪些关键来源没看？哪些观点重复？哪些例子太虚？哪些结论没有证据？这些都可以变成 loop 里的检查项。
## 2. 封面、缩略图和广告创意
Nate 展示了一个 thumbnail loop：让 Claude Code 先生成 10 个 YouTube thumbnail 概念，再按小尺寸清晰度、好奇心、情绪吸引力、视觉对比等维度打分，选出前三个，找出每个方案最弱的地方，继续改，再重新打分，最后收敛到一个更强版本。
这个场景很典型。AI 一次给 10 个创意并不难，难的是继续筛、继续改、继续比较。Agent Loop 的价值就在这里：它可以把“多方案 → 打分 → 选优 → 修改 → 再打分”变成一个自动循环。
但这里也有边界。创意评分有很强主观性，所以不能简单写“改到你满意为止”。更靠谱的做法是把评分拆细，或者用一个单独 checker agent 专门做评审。否则模型很容易自己给自己打高分。
## 3. 前端、3D 和可视化代码
Nate 的第二个例子是用 Three.js 做一个 3D 飞机。agent 不只是写代码，还要打开浏览器，检查飞机有没有渲染出来，能不能旋转、缩放，视角是否正常，然后继续改。
这类任务非常适合 Agent Loops，因为验证工具明确：浏览器、截图、console、测试、像素检查、交互检查。只要 agent 能看到结果，它就能从“我写完了”进入“我看过了，哪里不对，再改”。
我觉得这也是 Agent Loops 对产品开发最直接的价值。做 landing page、dashboard、组件库、数据可视化、Three.js 场景，都不应该只停在代码生成。真正可用的 workflow 是：生成 → 跑起来 → 截图 → 对照目标 → 修布局 → 再截图。
## 4. 视觉复刻和设计实现
Nate 还让 Claude Code 用纯 HTML/CSS 复刻 Beatles 的 Abbey Road 图片。它迭代了很多轮，也确实每轮都截图验证，最后能看到车、树、路、天空、斑马线这些元素，但结果依然不像原图。
这个例子反而很有价值：它说明 loop 不是魔法。只要验证标准和工具不够强，循环再多轮也只能把错误变得更有条理。
所以视觉复刻适合用 Agent Loop 做“结构、布局、颜色、元素关系”的近似实现，不适合拿它硬做照片级还原。如果目标本来就是图片质量，应该把 image generation、视觉模型、设计工具一起放进 loop，而不是只靠 HTML/CSS。
## 5. 视频剪辑和内容后期
Nate 说他自己最常用的 loop，是用 Claude Code 和 Hyperframes 做视频剪辑：拿 transcript，剪掉错误和停顿，做 beats，同步节奏，渲染，再检查每个 beat 是否在边界内、是否和 transcript 对齐。
这个场景我觉得非常值得关注。因为视频剪辑里有大量“人类很烦、机器可查”的细节：字幕有没有错位，停顿有没有切掉，转场是不是卡在错误位置，画面和脚本是否对齐，导出文件有没有问题。
它不是让 AI 一次性剪出最终大片，而是把剪辑流程里最机械、最需要反复检查的部分交给 loop。对内容团队来说，这比“AI 帮我写一个脚本”更接近生产力。
## 6. 脚本、文章和播客提纲
Nate 提到，如果是写 script，就不需要视觉验证，而是要检查 flow、voice、tone。这个场景看起来主观，但其实也可以拆成半客观：开头有没有说清矛盾，段落之间有没有断，例子是否具体，语气是否一致，是否有 unsupported claim，结尾是否能落到行动建议。
所以写作类 loop 的重点不是“让 AI 写到满意”，而是给它一张明确的审稿表。它每一轮都要按表检查，而不是凭感觉说更好了。
## 7. 团队代码库里的持续开发循环
Nate 也提醒，不是每个人都需要 24/7 的 agent fleet。对个人知识工作者来说，很多 loop 跑 30 分钟到 2 小时就够了。但如果是团队在一个真实代码库里持续开发，agent 长时间跑测试、修 bug、开 PR、检查回归，就会更合理。
这也是为什么别人说“我已经不 prompt agent，我写 loops”时，不一定能直接照搬。Peter Steinberger 这种重度工程场景，和普通内容创作者、运营、研究者的需求完全不同。
—
## 判断标准：先问它能不能被检查
> 不要先从多 agent 架构开始，而要先从“这个任务能不能被检查”开始。
一个任务适合 loop，通常有几个特征：目标可以描述清楚，过程可以拆成多轮，结果可以被工具观察，失败可以被定位，停止条件可以写出来。
反过来，如果你连什么叫 done 都说不清，或者 agent 没有工具检查结果，那就不要急着做 loop。那不是自动化，只是把不确定性放大。
这也是 Nate 这个视频最有价值的地方。他没有把 Agent Loops 讲成一个新名词，而是把它拉回到几个很实际的问题：你要它做什么？它怎么知道自己做完了？它每一轮怎么检查？什么时候必须停？
往后看，AI 产品真正的分水岭可能不只是模型多强，而是谁能把这些 loop 做成稳定工作流。
从 prompt 到 loop，本质上是从“让模型回答”走向“让系统交付”。

## 研究摘要

**TL;DR**：受 Nate Herkelman 啟發的七個 Agent Loop 最高可用場景實踐報告，核心論點：最關鍵的不是 repeat 而是 observe——無驗證的 loop 只是更貴更長時間的瞎忙。

### 核心論點

- **observe 先於 repeat**：沒有驗證（observe）的 loop 只是更貴更長時間的瞎忙；agent 會不停產出，但不知道什麼時候該停，也不知道每一輪是不是真的變好了
- **七個最高可用場景**（依 observe 難易度排序）：① 調研→產物循環 ② 封面/縮略圖/廣告創意 ③ 前端/3D/可視化代碼 ④ 視覺復刻/設計實現 ⑤ 視頻剪輯/內容後期 ⑥ 腳本/文章/播客提綱 ⑦ 團隊代碼庫持續開發循環
- **判斷標準四問**：「它能不能被檢查？它怎麼知道自己做完了？它每一輪怎麼檢查？什麼時候必須停？」——有確定性答案才適合 loop
- 本質轉變：從「讓模型回答」→「讓系統交付」；reason→act→observe 三步循環

### 關鍵數據 / 工具

- 受 Nate Herkelman YouTube 視頻啟發（含 LinkedIn 原文連結）
- reason→act→observe 三步循環（對應 workspace The Loop 的 TEST 階段）
- 案例：Nate 用 agent loop 讀多來源（文章/YouTube transcript/X post）生成視頻腳本
- 資料來源三個可驗證連結（YouTube + LinkedIn + Skool community）

### 批判性觀察

- observe 關鍵論點是本文最銳利之處，與 workspace The Loop 的 TEST/verifier 哲學完全對應
- 七場景橫跨內容創作/設計/開發，覆蓋面廣，但各場景技術細節較淺
- 文章較短（3K chars），適合快速場景定性，不適合作為技術實作參考
