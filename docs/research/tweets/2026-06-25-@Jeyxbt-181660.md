## 全文

## The people who built Claude don't treat a skill as a prompt you write once. They treat it as a folder that checks its own work - and the most important lesson is the part almost everyone skips.
> A common misconception we hear about skills is that they're just markdown files. The most interesting part is that they're not - they're folders with scripts, assets, and data the agent can discover and manipulate.
The makers of Claude just opened up their internal playbook. The engineers, the marketing team, the legal team - every one of them runs their workflows on Claude skills, technical and non-technical alike.
Pull all of it together - the interviews, the blog posts, the docs - and it collapses into five lessons. None of them require you to be an engineer. The hardest one isn't about writing a better prompt. It's about building the thing that grades the output.

---
# Lesson 1 - Understand the four types
Anthropic's team sorts skills into nine technical categories. That's the engineer's view. Underneath it, all nine collapse into four skill types - and these four work whether you write code or never touch a terminal.

[圖 1 — 來源: Four types. Orchestration is just the other three, stacked.]

| Type  | What it does  | Technical  | Non-technical  |
| --- | --- | --- | --- |
|  Utility |  One small, reusable task, often layered inside bigger skills | How to call a specific library or API  | "Draft this in my voice" · "Simplify this writing" |
| Verification  | Checks the final output before it ships  | Code-quality review  | Brand-voice check · style-guide review  |
| Data Enrichment  | Pulls external data in to make the output better  | Pull a site's traffic and conversion numbers  | Analyze competitors · pull recent reports  |
| Orchestration  | Chains the other three into one command  | "Generate report" → enrich → draft → verify  | Same - one trigger, three buckets behind it  |

An orchestration skill is the whole stack in one word. Say you build one called generate report. It pulls the analytics (enrichment), drafts the write-up (utility), then checks the branding and the numbers (verification). One command, three buckets working underneath.
Here's the trap that quietly breaks most homemade skills. The best skills fit cleanly into one type. The ones that try to do everything straddle two or three at once and confuse the agent. Specific skill, specific job. When in doubt, split it.
You don't have to sort yours by hand. Hand the agent this:
```
Look at my existing skills and my past chat history.
Identify the skills I already have and the ones I should build.
For each, tell me which of these four buckets it belongs in:
utility, verification, data enrichment, or orchestration.
Flag any skill that straddles two buckets, and rewrite its scope
so it falls cleanly into one.
```

# Lesson 2 - Use the power components
Most people think a skill is a markdown file. It isn't. A skill is a folder, and the interesting parts are the things sitting next to the text — scripts, assets, data the agent can open and run. Three of those components carry most of the weight.

[圖 2 — 來源: Not a markdown file. A folder with moving parts.]

1. Scripts
A script is plain code that runs to finish a task. From Anthropic:
> One of the most powerful tools you can give Claude is code. Giving Claude scripts and libraries lets it spend its turns on composition - deciding what to do next - rather than reconstructing boilerplate.
The real move here is partitioning the work. A deterministic step gives the same output for the same input every time - 2 + 2 is always 4. A script nails that perfectly. A non-deterministic step can give a different answer each run, which is exactly what you want from the AI.
So push the repeatable parts into scripts and leave the judgment to Claude. The more you move into code, the more repeatable your output gets and the fewer tokens you burn.

2. Templates
Drop a sample file into the skill's assets folder and Claude treats it as the shape of the output. If the target is a slide deck, hand it last quarter's deck - every future report fills that template. Change the template, and every output downstream changes with it. Same principle as scripts: the skill stops improvising and starts doing the same thing every time.

3. Setup prompts
You will forget how your own skill works. Build it so a human - future you - can pick it up cold. There's an old line in programming: any fool can write code a computer understands; good programmers write code humans understand. Same for skills. Anyone can write a skill Claude understands. The best people write skills that humans understand too. Three things get you there:
- config.json - on the first run, if a value is missing, the skill asks for it, then stores it. You never hand it over twice.
- Ask-user-question - for anything multiple-choice, tell the skill to use the ask-user-question tool. Claude shows clean structured options instead of a wall of free text.
- Arguments - declare an arguments field at the top of the SKILL.md. It's the reminder, to whoever runs the skill later, of exactly what input it needs.
When you build these, don't optimize for today. Optimize for the version of you running this skill in two or three years. Take the extra ten minutes now.
```
Audit every skill in my project.
For each one, tell me which of these three components it's missing:
1. scripts — for any deterministic step it currently does by hand
2. a template — if its output should always take the same shape
3. setup prompts — config.json, ask-user-question, or an arguments field
Then show me the smallest change that adds the highest-value one.
```

## Lesson 3 - Focus on the Verifier
This is the one Anthropic ranks above everything else. Straight from the blog post:
> Verification skills have had the most measurable impact on Claude's output quality internally. It can be worth having an engineer spend a week just making your verification skills excellent.
A week of an engineer's time on one skill that only checks output. That's how heavily they weigh it. The creator of Claude Code put a number on it: give Claude a way to verify its own work and you 2–3x the quality of what it produces.
Most people miss the next part. There are two kinds of verification, and you need both.

[圖 3 — 來源: Correctness is did it work. Quality is is it good. You need both.]

- Verify for correctness. Did it get the facts right? Are the numbers right? Is the app actually running? This is the quantifiable layer - true or false.
- Verify for quality. Does the output clear the bar you actually want? Most people treat AI as a multiplier: more output, same quality. The sharper framing is AI as an amplifier - same volume, higher quality. The verifier is what raises the bar on every single output.
Claude Code already ships two correctness verifiers: /verify runs your app and confirms a change does what it should, and /run launches the app so Claude can see its own work. The thing any good verifier needs is an objective output - something you or Claude can read as a clear result. A code reviewer that returns pass or fail. A report reviewer that returns a grade out of 10.
You can build a verifier from scratch, but the faster path is bolting verification onto a skill you already have. Take a brand-voice skill and add a check step - now running it returns a clean pass or fail against your voice. The strongest example in the whole playbook is one an Anthropic growth lead built: a skill that simulates feedback from their own manager. They fed Claude the manager's public writing and internal notes, and every week the skill returns the exact feedback she'd give. Her judgment, encoded as a reviewer. By the time anything reaches the real manager, it's already cleared her AI clone once.
> Audit my existing skills.
Tell me which ones could take a verification step that returns a clear
pass/fail or a grade out of 10. For each, write that step.
Then flag any external data the verifier would need to pull in
to actually judge the output, not just guess at it.

## Lesson 4 - Write the gotchas
A gotcha is a logged failure - a running list of things Claude got wrong inside a specific skill, written down so it never repeats them. Think of it as a "do not do this" section that grows over time.
> The highest-signal content in any skill is the gotcha section.
Here's the part that trips people up. You can't write the gotchas up front. These are the edge cases you haven't lived through yet - and the only way to find them is to actually run the skill and watch it break.

[圖 4 — 來源: Month one to month three. The skill gets sharper every time it breaks.]

> Most of our best skills began with a few lines and a single gotcha. Then they got better because people kept adding to them as Claude hit new edge cases.
So adding gotchas isn't busywork - it's a forcing function. You can't log a failure you never witnessed, which means the only way to grow the section is to keep using the skill and keep testing it. The skill that has the most gotchas is the skill you've actually run the most.
And resist the urge to pre-load a giant list to look thorough. If Claude hasn't done it yet, you don't need a gotcha for it yet. Wait, watch, then write the one that's real. A fake gotcha is just noise that makes the next failure harder to spot.
One frame to hold all of this together: the skill is the structure, the verifier is the leverage, and the gotchas are the moat. Anyone can copy your skill's structure. Nobody can copy the list of failures only you have lived through.

# Lesson 5 - Tune the trigger
The trigger is what makes a skill actually fire. Type a command and hit send - that's a manual trigger. Better is when Claude decides on its own that a skill fits the moment. To make that happen, you have to understand how it decides.
When Claude Code starts a session, it builds a list of every available skill paired with its description, and scans that list to answer one question: is there a skill for what the user just asked? Which means the thing most people get wrong is this:
> The description field is not a summary. It's a description of when to trigger the skill.
A good trigger does two things - it names who the skill serves and when it should fire. Look at how Anthropic writes the description for their front-end design skill:
```
Create distinctive, production-grade front-end interfaces with high
design quality. Use this skill when the user asks to build web
components, pages, or applications...
```
The load-bearing words are "use this skill when the user asks to build." Then it lists the actual phrases a real person would type. So now when someone says "build me a web page for this dashboard," Claude already has the match.

[圖 5 — 來源: The description is the match condition. Write the words you'd actually type.]

The rule writes itself: think about the exact words you'd type when you reach for the skill, and put those words in the description. Not a tidy summary of what it does - the trigger that makes it fire.
This is also how skills call other skills. An orchestration skill just references the others by name, and Claude runs them if they're installed. The discipline that keeps it clean: build orchestration out of smaller utility skills, not as one giant block. Ask "can I break this into sub-skills?" When you can, you get the payoff - update the utility skill once, and every orchestration that calls it updates for free.
```
Audit my skills' description fields.
For each, rewrite it as a trigger, not a summary: name who it serves
and the exact phrases I'd type when I want it to fire.
Then flag any skill doing too much that should be split into
smaller utility skills an orchestration skill can call by name.
```

# The shift underneath all five
Most people build a skill so Claude understands them - a cleaner prompt, written once, frozen in place.
The teams who built Claude do the opposite. They build skills that check their own work, name their own failures, and get sharper every time they break.
So here's the split worth betting on. Most people will spend this year polishing prompts. The ones who spend it building verifiers will be working at a quality bar the prompt crowd can't reach by the time they notice the gap.

## 研究摘要

**TL;DR**：Anthropic 內部 Skill 設計五課——4-type taxonomy、Skills = folder（三大元件）、Verification 最高槓桿（2-3x quality）、Gotcha = 護城河（只能 run-and-break 積累）、Description = trigger 非 summary；含 4 個可直接 paste 的 audit prompts。

### 核心論點

1. **4-Type Skill Taxonomy**（從 9 技術分類萃取）：
   - **Utility**：一個小可複用任務（layerable）
   - **Verification**：輸出出門前的把關
   - **Data Enrichment**：拉外部數據提升輸出品質
   - **Orchestration**：串接上三者的指揮官（Orchestration = 其他三種 stacked）
   - **原則**：最佳 skill 只屬一類；跨兩類的要拆分

2. **Skill = Folder，不是 Markdown 文件**：三大元件：
   - **Scripts**：確定性步驟→腳本；非確定性判斷→交給 Claude（分工原則）
   - **Templates**：assets 資料夾放範本文件，所有輸出自動對齊格式
   - **Setup Prompts**：config.json（一次設定後永久記住）+ ask-user-question 工具 + arguments 欄位

3. **Verification 是最高槓桿**：
   - 「Verification skills have had the most measurable impact on Claude's output quality internally」
   - 「值得工程師花一週只做 verification skill」
   - Boris Cherny: 給 Claude 自我驗證方式 → 品質 **2-3x**
   - **兩類驗證**：Correctness（量化 true/false）+ Quality（品質 amplifier，同量更高質）
   - **Manager simulation skill**：把主管的文字和內部 notes 餵給 Claude，編碼為 AI reviewer → 到達真實主管前已通過 AI clone

4. **Gotcha = 護城河**：
   - 「Highest-signal content in any skill is the gotcha section」
   - **不能事先寫**：只能 run-and-break 才能發現真實邊界案例
   - 「Fake gotcha = noise that makes the next failure harder to spot」
   - **框架**：Structure（任何人都可複製）+ Verifier（槓桿）+ Gotchas（護城河，只有你有）

5. **Description = Trigger Condition（非 Summary）**：
   - Claude 啟動時掃描 description 決定 skill match
   - 「Use this skill when the user asks to build...」+ 真實使用詞彙
   - Skills 呼叫其他 skills：orchestration skill 只 reference 名稱
   - 原則：「Can I break this into sub-skills?」能拆就拆 → 更新 utility skill，所有 orchestration 自動更新
