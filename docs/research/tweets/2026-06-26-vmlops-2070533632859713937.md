## 核心摘要

> Anthropic 工程師 Andrew 和 Ash 在 engineer conference 上，回顧過去一年 Claude 從「20 分鐘 agent」演進到「能持續運行數天」的技術歷程，並深度拆解他們內部的 Generator-Evaluator harness 設計模式。

- **三大瓶頸**制約 long-running agent：Context 有限性（記憶清除、Context Rot、Context Sense Anxiety）、規劃能力不足（無法完整執行多步驟任務）、模型無法準確評估自身輸出品質
- **Model + Harness 共演化**：從 Sonnet 3.7（1 小時）到 Opus 4.6（12 小時），模型能力提升與 harness 設計同步推進；harness 不會消失，而是隨模型能力演化
- **Generator-Evaluator-Planner 三角架構**：Planner 產生高階 sprint 規劃；Generator 逐 sprint 建構；Evaluator 用獨立 context window 進行對抗性評估，並與 Generator 協商「完成條件契約（Done Contract）」
- **自我評估是陷阱（Self-evaluation trap）**：同一 context 內的模型無法客觀評估自己的輸出；必須使用**對抗性獨立評估器**（adversarial evaluator），類比人類的「評論家比創作者更容易批評作品」
- 五個關鍵 takeaway：避免自我評估、compaction 不等於連貫性（structured handoff 更優）、品味（subjective quality）是可量化的（設計四維評分：design/originality/craft/functionality）、透過讀 traces 理解模型行為、前端設計技能可以用 rubric 系統化訓練

## 整理版（可讀逐字稿）

### 開場：Agent 長時運行的三大挑戰（00:00–02:43）

Andrew（Anthropic applied AI team，London）回顧 Boris（Claude Code 創始人）在 Claude Code 一週年時的感言：一年前 Claude 還在為 bash 命令和字串轉義掙扎、只能跑 20 分鐘，現在幾乎所有 Claude Code 都是 Claude Code 自己寫的，且能持續運行數天。

為什麼 agent 難以長時運行？Andrew 歸納三大挑戰：

1. **Context 限制**：Context window 有限，新 session 等於失憶；隨 session 深入出現「Context Rot」（連貫性衰減）；接近 context 上限時模型出現「Context Sense Anxiety」（急著收尾）
2. **規劃能力不足**：模型傾向一次性做完所有事，或做到一半停下；或是 context 耗盡後留下未完成的應用
3. **無法評估自身輸出**：模型傾向說你想聽的話；看到半成品功能也可能認為「看起來完成了」，或建了 UI 但 backend 根本不存在

### 解決之道：Model 與 Harness 的協同演化（02:43–15:18）

兩個主要解法：

**（一）改善模型本身**：「meter chart」顯示 agent 在最簡 scaffold 下完成 50% 任務所需時間，從 Opus 3.7 的約 1 小時，到 Opus 4.6 的 12 小時（代表整個工作日）。

**（二）改善 Harness（腳手架）**：Anthropic Agent SDK 提供核心原語：agent loop（決定用哪些工具）、MCP server、sub-agent 委派、Claude.md / skills / slash commands 載入、權限系統。

重要里程碑回顧：
- **Sonnet 3.5**：第一個展現實際 coding 能力的模型，能看自己的輸出並迭代（pre-Claude Code 時代的 aha moment）
- **Computer Use**：能截圖、點擊、測試自己的程式碼
- **Claude Code（Feb 2025）**：以 Sonnet 3.7 發布，最初定位是「實驗性工具，用來了解開發者如何使用 Claude 進而改善基礎模型」
- **Ralph Loop（Jeffrey Huntley 技術）**：「deterministically bad is better than unpredictably good」——可預測地失敗優於不可預測的成功。Claude Code 內建了 Claude 版本的 Ralph Loop plugin（單 session 內靠 compaction 維持，並非嚴格的 fresh context window 版本）
- **Claude Code 2.0**：加入 Checkpoints，模型更能追蹤自身 token 消耗、管理 context
- **Haiku 4.5 + Opus 4.5**：sub-agent 經濟性大幅提升，能跑約 30 小時
- **Sonnet 4.6 + Opus 4.6**：Opus 4.6 被定位為最「agentic」的模型，能決定使用哪些工具、運行更長時間；Agent Teams（sub-agent 間直接溝通）、Server-side Compaction（可無限運行）、1M context GA

### Ash 接棒：Generator-Evaluator 架構的技術細節（15:18–36:38）

**核心洞察：自我評估是陷阱。**

模型在自己建構的 context 內無法客觀評估自己的輸出。解法類比人類直覺：批評一頓飯比自己烹飪容易多了——因此要**獨立訓練一個嚴格的 critic（evaluator）**，而非要求 builder 自我批評。

**設計品味的量化**：前端 UI 常被認為是主觀的，但只要有強烈觀點就能量化：四維評分（Design / Originality / Craft / Functionality），並有意識地根據模型特性調整權重（例如 Opus 4.6 功能性已很強，所以更強調 Design 和 Originality）。評估器可以用參考網站校準品味，防止 AI slop（紫色漸層、一般性 AI 美學）。

**GAN 式 Harness 的優勢**：Generator 卡在某個維度（如 originality 持續低分）時，adversarial harness 會直接丟棄重來——這是 single-agent loop 或 Ralph Loop 做不到的。

**加入 Planner 後的完整架構**：

1. **Planner**：將一行提示詞展開為高階 sprint 清單（刻意不細化技術細節，避免早期規劃錯誤沿 sprint 級聯放大）
2. **Generator + Evaluator 協商 Done Contract**：在 Generator 開始寫任何程式碼前，Generator 提出「我要做 X，你測試 Y」，Evaluator 可能回推「scope 太大、測試太弱、漏掉邊界條件」，兩方協商直到達成明確的完成條件
3. **Generator 建構**：Evaluator 對照 Done Contract 評分，而非對照原始 spec
4. **Evaluator 實際使用 app 測試**（Playwright MCP）：找到只有真正使用才能發現的 bug

**Opus 4.6 帶來的架構簡化**：原本複雜的 per-sprint evaluator 設計在 Opus 4.6 下可以大幅簡化——模型能在 2 小時連續 build 中保持連貫性，不再需要強制 per-sprint 評估。一個連續 session 就足以處理非常長的建構任務。

### Q&A 精華（36:38–01:10:07）

**評估器是 per-project 還是可重用？** 目標是可重用：找出模型的共通弱點（如前端設計品質），而非針對特定 app 定制。

**Context Rot 和 smart zone 問題**：Ralph Loop 的核心思想是讓模型保持在 context 的「smart zone」（前 40%）。但 Ash 認為這是暫時問題——Opus 4.6 已能在更長的 context 內保持連貫。Server-side compaction 讓這個問題更接近解決。

**Human in the loop**：目前的探索方向是「能做到完全自主的程度嗎？」若需要插入人工，Hooks 是最自然的原語（特定 stop condition 觸發 evaluator 把控制權交回人類）。但也可以採取「跑 10 個平行版本，人工挑選成功的 3 個」模式。

**讀 traces 的重要性**：真正理解模型行為需要逐行讀 traces——「把自己放進模型的位置」，像閉著眼睛瀏覽網頁一樣。這是 Ash 在 Anthropic 內部開發 Chrome agent 時的核心實踐。

**Brownfield vs Greenfield**：目前這個 harness 模式最適合 greenfield 新應用；brownfield（既有代碼庫）需要更多控制和定制化的 rubric。
