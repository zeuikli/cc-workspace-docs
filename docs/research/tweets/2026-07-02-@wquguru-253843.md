## 全文摘要（原文 8,357 字，節錄核心技術段落）

用好 Fable 5，離不開三塊：提示詞工程（邊界設計）、長時間運行上下文管理（檢查點/記憶/進度驗證）、Loop（/goal + /loop + 並行子代理）。

### 第一部分：理解 Fable 5 能力跃迁

六項能力跃迁（vs Opus 4.8）：
1. **長時間自主運行**：設計目標為「跨越多天的目標導向任務」
2. **首次正確率**：複雜但定義清晰的問題一稿就對
3. **視覺理解**：密集技術圖像/網頁截圖解讀大幅提升，使用更少 output token
4. **企業工作流**：財報/表格/文檔，更守指令、不越界
5. **代碼審查**：跨 codebase bug 召回率更高（注意：進攻性網安被安全分類器規避）
6. **委派與協作**：可穩定管理 50+ 並行子代理，支持異步通信

**舊 Prompt 失效原因**：Opus 4.8 時代的逐條限制對 Fable 5 是天花板。原則：**少寫指令，多給意圖**。

### 第二部分：寫好 Fable 5 Prompt

**四要素結構（最小可行框架）**：

```plaintext
我正在為[服務對象]做[更大的任務]。
他們需要[這份輸出用來支撐什麼]。

請求：[一句話說清你具體要什麼]

輸出格式：[結果如何組織和交付——篇幅、結構、風格]

約束：[過程中絕不允許發生的事——不做什麼、不假定什麼]
```

**Effort 選擇法則**：先按默認 high 跑；超時或「順手優化」太多降到 medium；質量要求極高上 xhigh；**不要在簡單任務上用高 effort**（Fable 會收集不需要的上下文並反覆推敲）。

### 第三部分：管好長時間自主運行上下文

**檢查點**（官方推薦最簡寫法）：
```
在你繼續之前先暫停。列出你計劃採取的行動，
讓我確認後再繼續
```

**進度驗證**（防虛報進度）：
```
沒有對應工具結果支撐的事項，標注為"未驗證"，不要報告為"已完成"。
```
→ 核心原理：把聲明和證據綁定，模型不能只說「測試通過了」，必須確認真的運行了測試。

**記憶系統**（最高回報的基礎設施，一個 Markdown 文件夾即可）：
```
把本次工作中學到的經驗寫入 notes/ 目錄：
每條經驗一個文件，頂部一行摘要。
被糾正的錯誤和驗證過的有效方法都要記錄，並寫明為什麼重要。
倉庫或聊天記錄裡已有的信息不要重複。
優先更新已有筆記，而不是新建重複條目。
被證明是錯的筆記要刪除。
```

**Overnight 總結風格**（長時間無人在場後的輸出格式）：
```
如果你已經長時間在用戶不在場的情況下工作
（跨夜、跨大量工具調用、自他們上次發言以來），
你的最終消息是他們對這一切的第一眼。
把它寫成重新鋪墊，而不是工作線程的延續：
先說結果，再說需要他們做的一兩件事，每件都當作新信息來解釋。
寫完整句子。拼出術語全稱。不要用箭頭鏈、連字符堆疊的複合詞。
```

### 第四部分：設計 Loop

**Claude Code 四種循環**：
1. 回合制（手動檢查 → 下一輪指令）
2. 目標制 `/goal`：一直迭代到條件達標
3. 定時制 `/loop`（本地）/ `/schedule`（雲端）
4. 主動式：schedule + goal + Dynamic Workflows + Auto mode 組合

**`/goal` 最佳實踐**（確定性標準最有效）：
```plaintext
/goal 把首頁 Lighthouse 性能分數提到 90 以上，最多嘗試 5 次
/goal 修復所有失敗的集成測試，最多迭代 8 輪。每輪結束後列出剩餘失敗的測試數量和失敗原因。
```

**四件套示例**（處理用戶反饋流）：
```plaintext
/schedule 每小時執行一次：
檢查 #project-feedback 頻道的新 bug 報告。
/goal 本輪發現的所有報告都完成分類、處理和回復才算完成。
修復 bug 時，用 Dynamic Workflow 並行在三個獨立工作樹中探索方案，
由一個裁判代理做對抗性審查，選擇最優方案。
用 auto mode 運行，全程不請求人工確認。
```

**並行子代理三原則**：
1. 能拆成並行任務的就拆
2. 異步通信優先（不阻塞等待子代理返回）
3. **用獨立驗證替代自我批評**（全新 context 的驗證子代理 > 主代理自我審查）

### 第五部分：避坑

**⚠️ 重要：復述推理會觸發 Fallback 到 Opus 4.8**
任何 prompt/skill/系統提示裡含「展示你的思考過程」「解釋你的推理」類指令，可能觸發 `reasoning_extraction` 拒絕類別，導致請求 fallback 到 Opus 4.8。**遷移到 Fable 5 時必須審計所有舊 skill 和系統提示**，移除這類指令。

**偶發的提前停止**：
```plaintext
如果你陳述了下一步意圖，必須立即執行對應的工具調用，
不要以純文字意圖結束回合。
已有足夠信息時不要請求許可，直接推進。
```

**上下文預算焦慮**：
```plaintext
不必為上下文預算擔心。按當前任務的完整需求工作，
不要因為節省上下文而壓縮、總結或提前移交你的工作。
```

**安全分類器三組**：進攻性網絡安全、生物/生命科學、思考內容提取 → 建議 production 回退到 Opus 4.8。

## 研究摘要

**TL;DR**：Fable 5 實戰完整指南（中文）：四要素 prompt 框架、notes/ 記憶系統、overnight 總結風格、/goal /loop /schedule 組合、並行子代理三原則；最重要的避坑是 reasoning_extraction 指令會觸發 Fable→Opus 4.8 fallback。

### 核心論點

- Fable 5 舊 prompt 失效原因：逐條限制是天花板，改為「多給意圖少寫指令」
- 進度驗證：聲明與工具結果綁定，防虛報（「未驗證」標注機制）
- notes/ 記憶系統是 Fable 5 上回報率最高的基礎設施
- reasoning_extraction 是 Fable→Opus fallback 的隱藏觸發條件（遷移必審舊 skill）
- 驗證子代理必須用全新 context（驗證者不能是執行者）

### 關鍵數據 / 工具

- `/goal 把首頁 Lighthouse 分數提到 90，最多嘗試 5 次`
- `/schedule 每小時 + /goal + Dynamic Workflows + auto mode` 四件套
- 成本控制六策略：按任務選模型、明確停止條件、小批量試點、確定性工作交腳本、輪詢間隔≥變化頻率、定期 /usage 復盤
- 作者提供 Skill：`npx skills add https://github.com/wquguru/skills --skill fable5-best-practice`

### 批判性觀察

- reasoning_extraction 避坑與本 workspace core.md 的「禁止要求展示推理」規則高度對齊，值得直接補進規則
- notes/ 記憶系統與 MEMORY.md/LESSONS.md 雙軌機制有重疊，需釐清分工
- overnight 總結風格 prompt 是少見的「多 agent 長時間任務後的輸出規範」，可封裝為 subagent-strategy.md 規則
