## 全文

I recently had a really enjoyable day expanding my use of loop engineering in @DevinAI . Previously, I used loops only for a single module while I was at my computer. For this task, I used the approach to deliver an entire application: 24 tickets over 27 hours of continuous execution without my intervention.
This post describes my setup and shows how the workflow works which can be apply anywhere.

## Problem

Much of the time, especially when working with multiple coding agents, the human acts only as a relay: copying and pasting reports from one agent to another.
Loop engineering automates that flow so the human can stay hands-free.

## Base knowledge

Every loop requires two types of agents:
- `Orchestrator`: Oversees the loop, dispatches work, and passes messages among the actors.
- `Actors`: In this case, there are two: a reviewer and a programmer.
We define the loop in a prompt, give it to the orchestrator, and let it run.

## Coding agents

You should be able to use this flow with Claude, Codex, or Devin. In general, any coding agent that supports an async_task tool (a mechanism that lets an agent start a task and check its status later) should support this usage pattern out of the box.
@DevinAI has an advantage here because its actors can use models from completely different model families. For example, you can compose a flow using OpenAI, Anthropic, and open-source models together.

## Tickets

It is best to prepare your tickets in advance. I spent almost half a day using the Wayfinder skill from @mattpocockuk create these 24 tickets. Then used his TDD skill for the programmer subagent to do the work.
My tickets live in the repository as Markdown files, but as long as your agents support it, they could come from GitHub, Jira, Linear, or elsewhere. These tickets define the work.

## Setup

We ask Devin to create subagents in `~/.config/devin/agents`, each with a specific model and prompt. It can be shared among all your repos.
For example:
Create a subagent named programmer using `glm-5.2` with this prompt: "You are a senior software engineer". With Codex and Claude, you do not need this setup step; you can specify the model directly in the prompt. However, creating named subagents gives you reusable building blocks with distinct prompts and models.
For Devin, the glm-5.2 portion is critical because it is the model ID and must match exactly. You can choose from models such as:
- adaptive
- claude-fable-5
- claude-opus-4.8
- gpt-5.5
- glm-5.2
There are many more available. Run `/models ABC` to explore them.
I created three:
- programmer: glm-5.2
- codex-reviewer: gpt-5.5

## Loop design

The loop is a prompt which should be composable for your workflow.
For example, I have one linear flow where tickets must be implemented in a specific order. In another session, I split the work into lanes that run in parallel, while reusing the same loop for each ticket.
The prompt contains four parts. Its purpose is to clearly tell the orchestrator what to repeat and when to stop:
- Context: What are we doing?
- Workflow: Describe the loop. In my case:
- Coding instructions: Add any project-specific instructions here.
- Goal: Define when the orchestrator should finish.

## Actual loop

- The programmer writes the code and provides a report.
- The orchestrator sends the programmer's report to the reviewer.
- The reviewer performs the review.
- The orchestrator sends the reviewer's feedback to the programmer for fixes.
- The loop repeats until there is nothing left to fix.
- Once the reviewer approves, the orchestrator tells the programmer to close the ticket and commit the work.
- Every time the orchestrator receives reviewer feedback, it checks whether the reviewer is satisfied. If so, it moves to the final phase of the ticket. Otherwise, it passes the feedback to the programmer for fixes.
- Some tickets take several rounds to resolve all issues, but that is no longer a manual process.
- The orchestrator starts fresh subagents for the next ticket. This helps preserve context-window capacity: one subagent handles one ticket, regardless of role.

## Loop them all

For planning, I used Fable 5 Medium.
My loop setup was:
- Orchestrator: glm-5.2
- Reviewer: gpt-5.5
- Programmer: glm-5.2
This keeps the pipeline context separate from the ticket context, preventing either from becoming bloated.
The running log looked like this:
> ⏺ Subagent: Ticket 15: turn-service
⏺ Ran programmer subagent Ticket 15: turn-service
Ticket 15 implementation done. Starting the reviewer.
⏺ Subagent: Review ticket 15
⏺ Ran codex-reviewer subagent Review ticket 15
Sending feedback to the programmer.
⏺ Subagent: Fix ticket 15 review issues
⏺ Ran programmer subagent Fix ticket 15 review issues
⏺ Subagent: Re-review ticket 15 fixes
⏺ Ran codex-reviewer subagent Re-review ticket 15 fixes
Reviewer approved. Instructing the programmer to finalize and commit.
⏺ Subagent: Commit ticket 15
⏺ Ran programmer subagent Commit ticket 15
Ticket 15 committed. Moving to ticket 16.
⏺ Updated todo list (24 items)

Once all finished, I will use Codex/Opus/Fable to do a review for all commits, in which I will check if there are review feedback are good or not this time. In the end, followed by my quick check for the codebase as the ending phase.

## 研究摘要

**TL;DR**：orchestrator 派工、programmer/reviewer 兩 actor 互審的 loop，24 張票、27 小時無人值守跑完一整個 app。

### 核心論點

- Loop = Orchestrator（派工 + 傳訊）+ Actors（programmer、reviewer），prompt 定義四段：Context / Workflow / Coding instructions / Goal，明確告訴 orchestrator「重複什麼、何時停」。
- 每張 ticket 走 programmer 寫 code→reviewer 審→有問題退回 programmer 修→再審，循環到 reviewer 核可才 commit，全程不需人工中繼訊息。
- 每張新 ticket 都開全新 subagent（不重用前一張的 context），刻意用「一票一 agent」保護 context window 容量。
- Devin 的優勢是 actor 可跨模型家族混搭（本例：Orchestrator=glm-5.2、Reviewer=gpt-5.5、Programmer=glm-5.2），刻意讓 pipeline context 與 ticket context 分離避免膨脹。
- Ticket 提前用 Wayfinder skill 產生、TDD skill 執行；全部跑完後另外用 Codex/Opus/Fable 對所有 commit 做一輪總審。

### 關鍵數據 / 工具

- 案例規模：24 tickets、27 小時連續執行、零人工介入。
- 模型組合：Orchestrator glm-5.2、Reviewer gpt-5.5、Programmer glm-5.2；規劃階段用 Fable 5 Medium。
- 工具/skill：Wayfinder（拆票）、TDD skill（programmer 執行）、Devin `~/.config/devin/agents` 具名 subagent 設定。
- Loop prompt 四段結構：Context / Workflow / Coding instructions / Goal；提及可用 lane-based 並行變體。

### 批判性觀察

- 核心模式（orchestrator 派工 + programmer/reviewer 互審迴圈 + 每票新開 subagent 保護 context）與本 workspace 的 Workflow 工具 `pipeline()`/`agent()`/對抗式驗證模式高度同構，可直接對照 subagent-strategy.md 的委派拓補與 quality-pipeline skill 的 gate 設計。
- 實測數據具體（24 票/27 小時、真實 running log 貼出），但全文未附成功率、review 輪數分布或失敗案例，證據偏「單次個人實測心得」而非可重現基準。
- 「一票一全新 subagent」與本 workspace core.md 的 fan-out 紀律（child 間不互通、失敗回 parent、不 self-retry）方向一致，但本文未處理 partial-failure 偵測（reviewer 誤判、programmer 卡死如何升級），屬缺口。
- Prompt 本體只給出結構描述與外部 GitHub Gist 連結，未內嵌完整 prompt 全文，本次歸檔無法附上可直接複製的模板，需要時得另外抓取該 Gist。
