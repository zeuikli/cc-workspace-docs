## 全文

Dynamic workflows, subagents, and verification - the way one founder swapped a whole language out in 11 days.
One founder pointed a fleet of Claude agents at a real production runtime and swapped the whole language out - 500k+ lines of Zig rewritten in Rust in 11 days. Bun's Jarred Sumner didn't hand-write it. He orchestrated it.
The wild part isn't the size - it's that the plan lived in a script, not a context window: a graph of jobs that fanned out across hundreds of agents, checked each other, and folded into one answer.
That's graph engineering, and Claude Code ships the tooling for it now. Here's the whole thing in 7 steps.

## Step 1 - Know when to stop prompting
[圖 1]
Subagents already fan out and come back - Claude delegates to a fleet, they run once, it merges. So a single fan-out is not the reason to reach for a workflow.
The reason is what happens after the fan-out. The moment one stage's result decides the next - route this, score that, filter, loop, retry, verify - you've stopped prompting and started orchestrating.

---

## Step 2 - Move the plan into code
[圖 2]
A dynamic workflow is a plain JavaScript script that Claude writes for the task you describe, and a runtime runs it in the background while your session stays free. The loop, the branching, the intermediate results - all of it lives in the script.
That's the difference from just spawning more agents. With subagents, Claude is the orchestrator and every result lands in its context window. At a handful that's fine; at fifty the window fills and the model starts fighting to stay on task. A workflow keeps the intermediate mess out of the window entirely -  so it scales to hundreds without drowning.
```
ultracode : audit every endpoint for missing auth
```
```python
/deep-research <question>
```
You start one by saying "use a workflow…" or dropping the keyword ultracode into your prompt. Requires Claude Code v2.1.154+, on all paid plans (on Pro, flip it on in /config).

## Step 3 -Give every agent a contract
[圖 3]
A node you can't reason about is a node you can't wire into a graph. The fix is a contract. When you hand an agent() call a JSON schema, the subagent is forced to return structured data in that exact shape - and if it doesn't match, the runtime retries instead of handing you a wall of text to clean up.
This is the quiet difference between a node a graph can consume and a node that only works when a human reads its output.

## Step 4 - Fan out -then pick pipeline over barrier
[圖 4]
This is t makes everything wait for the slowest node before the next stage starts. ## Step 5 - Put a skeptic on every finding
[圖 5]
The real leverage of a graph isn't more agents - it's the structure you can wrap around them to earn confidence. A verifier sits on the edge before a result is allowed downstream, and its only job is to try to kill the finding. If it survives, it passes. If not, it never reaches the answer.
The bundled /deep-research workflow is exactly this pattern shipping in production: fan out across angles, cross-check the sources against each other, vote on every claim, and filter out the ones that didn't survive. As of a recent build, a claim the verifiers can't check gets listed as unverified rather than silently dropped.

---

## Step 6 - Isolate the writers
[圖 6]
Reading in parallel is free. Writing in parallel is where things break. When many agents edit files at the same time, they collide. The fix is isolation: each agent gets its own copy of the tree - a git worktree - does its work there, and merges cleanly at the end.
Sumner's Bun port leaned on exactly this: at peak, several workflows ran at once, each in its own worktree, so hundreds of file-ports never trampled each other.

---

## Step 7 - Converge, tier the models, save the run
[圖 7]
Some jobs are unknown-size - a bug sweep where fixing one reveals three more. That needs a loop, and a loop that doesn't converge is just a budget on fire. The pattern that converges: keep going until two rounds in a row surface nothing new, then stop.
Not every node needs your best model. Run the boring, repetitive nodes on something cheaper and spend the expensive tokens where judgment actually lives. Check /model before a big run and route stages down where you can.
And when a run does what you wanted, save it. It lands in .claude/workflows/, version-controlled, and becomes a /name command anyone who clones the repo can launch. The graph you drew once is now infrastructure.

---

## The whole thing, on a real codebase
[圖 8]
Every step above shows up here. One workflow mapped the correct Rust memory lifetime for every struct field. A second dispatched hundreds of parallel agents to write behavior-identical .rs files, with two adversarial reviewers assigned to each output.
A fix loop drove the build and tests until they passed. And after the port landed, another workflow ran overnight hunting unnecessary data copies and opening PRs.

## Prompter or architect?
The linear agent - step one, step two, step three, each waiting politely for the last - was never the ceiling. It was just the first shape, the one everyone reaches for because it matches how we type.
Once you can see the nodes and the edges, you stop asking the agent to do more and start asking the graph to do it wider: fan out where the work is independent, put a skeptic on the edge where confidence matters, tier the models where judgment doesn't.
Most people will keep queueing steps in a line. The ones who learn to draw the graph will run a fleet.
