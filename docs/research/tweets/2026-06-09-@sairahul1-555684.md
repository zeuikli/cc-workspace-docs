## PART 1: WHAT IS A LOOP?

A loop is not a single agent call.

A loop is when the agent keeps going until something is actually true.

The shortest version:

→ You define what DONE means

→ The agent works toward it

→ A separate part of the system checks if it got there

→ If not: it tries again

→ If yes: it stops

One turn. One attempt. One shot.

That's how most people use AI.

A loop is different.

→ Write the function 

→ Run the tests 

→ Fix what fails 

→ Run the tests again 

→ Keep going until all tests pass

That's a loop.

Not more prompting. A self-improving cycle.

## PART 2: THE TWO KINDS OF LOOPS

Open Loop vs Closed Loop

Open Loop: The agent explores freely.

→ No hard stop condition

→ Powerful, but expensive

→ Best for research and discovery

→ Needs near-unlimited token budget

Closed Loop: The agent runs until a verifiable condition is true.

→ Tests pass

→ Lint is clean

→ Schema matches

→ PR is open

→ Ticket is updated

→ These are not feelings. They are binary checks.

This is the one that actually works for most people today.

The open loop is powerful.

The closed loop is what pays off.

## PART 4: THE 5-PART ANATOMY OF A GOOD LOOP

Every reliable loop has exactly five things:

1. GOAL — What done means precisely.

"All tests in test/auth pass and lint is clean"

Not "write authentication". Not "make it work".

A condition the system can check — pass or fail, true or false.

Vague goals create infinite loops.

Precise goals create reliable ones.

2. CONTEXT — What the agent knows before it starts.

→ VISION.md — what success looks like

→ ARCHITECTURE.md — the tech stack and folder structure

→ RULES.md — what the agent is never allowed to do

Without context: the loop guesses.

With context: the loop acts on intent.

3. ACTION — What the agent is actually allowed to do.

Files it can read. Files it can write. APIs it can call. Commands it can run.

Narrow the action space. Narrow the failure space.

4. FEEDBACK — How the loop knows if it worked.

→ Tests that pass or fail

→ Type errors that surface or don't

→ Lint warnings that appear or disappear

→ Structured errors the agent can read and act on

Not feelings. Not vibes. Binary signals.

5. STOP CONDITION — When the loop knows it's finished.

A separate evaluator — not the agent that did the work — checks the goal condition.

This is what /goal does under the hood.

A fresh model decides if you're done.

Not the one who wanted to be done.

## PART 5: THE 6 THINGS YOU ACTUALLY BUILD

1. AUTOMATIONS

This is the heartbeat.

Automations trigger discovery and triage by themselves.

→ Claude Code: /loop, /schedule, hooks, GitHub Actions

→ Codex: Automations tab — pick project, prompt, cadence

Daily loop examples from real teams:

→ Scan CI failures and write summaries

→ Triage open issues by severity

→ Hunt bugs added in the last 24 hours

→ Write commit briefings for the team

Without automations: you are the trigger.

With automations: the system surfaces the work.

2. WORKTREES

This is what prevents chaos when you run parallel agents.

Two agents writing the same file is the same headache as two engineers committing to the same lines without talking.

A git worktree is a separate working directory on its own branch — sharing the same repo history.

One agent's edits cannot touch the other's checkout.

→ Claude Code: --worktree flag, isolation: worktree on subagents

→ Codex: worktree support built in

Your review bandwidth is still the ceiling.

Worktrees remove the collision.

You remove the bottleneck.

3. SKILLS

This is how you stop re-explaining your project every single time.

Both tools use the same format: a folder with a SKILL.md inside — plus optional scripts, references, assets.

Without skills: the loop re-derives your whole project from zero every cycle.

With skills: it compounds. The agent knows your project before it starts.

→ VISION.md — what success looks like

→ ARCHITECTURE.md — the tech stack and folder structure

→ RULES.md — what the agent is never allowed to do

4. PLUGINS AND CONNECTORS

This is what makes EXECUTE real — the loop acts in your actual environment, not just your filesystem.

A loop that can only see the filesystem is a tiny loop.

Connectors (built on MCP) let the agent read your issue tracker, query a database, hit a staging API, drop a message in Slack.

This is the difference between an agent that says "here is the fix" and a loop that opens the PR, links the Linear ticket, and pings the channel once CI is green — by itself.

5. SUBAGENTS

This is what makes VERIFY honest — the checker is never the same agent as the maker.

Keep the maker away from the checker.

The model that wrote the code is too nice grading its own homework.

A second agent with different instructions — sometimes a different model — catches the stuff the first one talked itself into.

The split that works:

→ One agent explores

→ One agent implements

→ One agent verifies against the spec

This is also what /goal does under the hood.

A fresh model decides if the loop is done — not the one that did the work.

6. MEMORY

This is what makes the loop persistent — DISCOVER on run 47 knows everything runs 1 through 46 already tried.

The spine of the whole loop.

A markdown file. A Linear board. Anything that lives outside the single conversation.

The model forgets everything between runs.

The repo does not.

The memory file holds: what got tried, what passed, what is still open.

Tomorrow morning the loop picks up where today stopped.

It sounds too simple to matter.

Every long-running loop depends on it.

## PART 7: PROMPT ENGINEER VS LOOP ENGINEER

Prompt Engineer:

→ Craft better instructions → Linguistic skill → Better prompt → better single output → Still reviews output manually after every run → You are the feedback loop

Loop Engineer:

→ Design better feedback cycles → Software engineering skill → Better loop → reliable verified outcomes → System runs, checks, and self-corrects → The system is the feedback loop

The tools are the same. The mindset is completely different.

Prompt engineers ask AI for output.

Loop engineers design systems that produce verified outcomes.

The highest-paid AI engineers in 2026 are not writing better English sentences.

They are writing the logic that governs how agents discover, plan, check their own work, and know when they are done.
