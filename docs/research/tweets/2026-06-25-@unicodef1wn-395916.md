## 全文

One Claude in one window is the slowest way there is: type a request, wait, fix it, ask again, all by hand. That works until the task gets big. Then one Claude in one window starts to crack, and you feel it without knowing why. Workflows are the fix.
Anthropic shipped dynamic workflows in Claude Code. Claude now writes its own harness on the fly, custom-built for the task in front of it.
The default harness was built for coding, and it carries you far, because a lot of work looks like coding underneath. But some jobs break it: long-running ones, massively parallel ones, adversarial ones with a strict rubric. Workflows are how you get past that line.
Here is the part most people miss. You are not configuring a tool. You are asking Claude to build the tool, then run it.

## Why one window cracks
Ask the default harness for something large and it plans and executes in the same context window. The longer it works in that one window, the more three failure modes set in.
Agentic laziness. Claude declares victory after partial progress, closing 20 of 50 items in a review and calling it done.
Self-preferential bias. Ask Claude to grade its own output against a rubric and it favors its own findings.
Goal drift. Across many turns, especially after the context compacts, the objective blurs. Each summarization step loses something, and the "don't do X" you wrote at the start quietly falls off.
A workflow kills all three by structure, not willpower. It splits the job across separate Claudes, each with its own clean window and one narrow goal. The orchestrator holds the plan; the workers hold the work; a separate checker grades it.

---
## You don't need to code to use this
The first thing people assume: this is a developer toy. It isn't. A workflow is just Claude coordinating a team of Claudes, and the jobs that need a team are everywhere. Paste any of these into Claude Code and watch it build the harness itself.

[圖 2]

Ranking a pile of stuff.
> "Here's a folder of 80 resumes. Use a workflow to rank them for the backend role, then double-check the top ten. Interview me with questions to build the rubric first."
One agent reads each resume in its own window, a tournament ranks them by comparing pairs, and a checker re-reads your top ten so nothing good slipped through. You sort a thousand support tickets the same way.
Fact-checking your own writing.
> "Go through my blog draft and use a workflow to verify every technical claim against the codebase. I don't want to ship anything wrong."
One agent pulls out every factual claim, then a separate agent checks each one, then a third rates whether the source was solid. The writer who made the claim never gets to wave it through.
Mining a backlog nobody reads.
> "Dig through #incidents in Slack for the last six months and use a workflow to find recurring root causes where nobody filed a ticket."
This isn't only for engineers. Swap Slack for your sales numbers ("why did revenue drop in March?") or a failed process, and the same shape runs the post-mortem: separate agents form theories from separate evidence, then argue them out.
Naming things and other taste calls.
> "Brainstorm 30 names for this tool, then run a workflow tournament to pick the top 3 against a rubric."
Naming, design, copy, anything where the answer is a judgment call. Claude generates a spread, a review agent scores them against what "good" means, and a bracket picks the winner. No single agent falls in love with its own idea.
Turning your mistakes into rules.
> "Use a workflow to go through my last 50 sessions, find the corrections I keep making, and turn the recurring ones into rules."
It clusters the corrections, checks each candidate rule against a real past mistake, and keeps only the ones that would have caught something. The survivors go into a file Claude reads every time.

## The six patterns it composes from
Under the hood Claude assembles every workflow from a small set of blocks. Learn these six and you can read any workflow it writes, and steer it toward the shape you want.

[圖 3]

1. Classify-and-act. A classifier decides what kind of task this is, then routes to the right agent.
1. Fan-out-and-synthesize. Split into many small steps, run an agent on each, then merge. The merge waits for everyone, so the steps never cross-contaminate.
1. Adversarial verification. For every agent that makes something, spawn a second one whose only job is to attack it against a rubric. The single most useful move in the kit.
1. Generate-and-filter. Make many, drop the duplicates, keep only the tested survivors.
1. Tournament. Agents compete on the same task, a judge compares them in pairs until one wins. Comparing beats scoring.
1. Loop until done. When you don't know how much work there is, keep going until a condition holds: no new findings, no errors left. Not a fixed counter.

---
## Keep the maker away from the checker
Everything above rests on one move you cannot make inside a single window: split the agent that does the work from the agent that judges it.
One Claude that writes the fix and then grades the fix will pass its own fix. That's self-preferential bias, and no prompt talks it out of that. A workflow hands the output to a checker with no stake in it. Same trick powers debugging: spawn agents to form theories from separate evidence, one on logs, one on files, one on data, then send each theory to a panel of verifiers and refuters. Nobody gets to fall in love with their own answer.
## When to skip it
Workflows burn more tokens. A panel of five reviewers is overkill for a normal bug fix. Before reaching for one, ask whether the task really needs more compute. Most don't. Save workflows for the jobs that defeat a single window: the migration, the thousand-row sort, the report you can't afford to ship wrong.
## The shift
Static workflows came first, hand-wired with the SDK, generic enough to cover every edge case. With Opus 4.8, Claude writes a custom harness for your exact job instead. Pair it with /goal for a hard finish line and /loop to run on a schedule. Cap the cost by telling it "use 10k tokens." Save one by pressing s in the menu, then ship it inside a skill so your team reuses it.
The old job was writing the prompt. The new job is designing the team and letting Claude build the harness that runs it.

## 研究摘要

**TL;DR**：動態 Workflow 解析——三大單視窗失敗模式（Agentic laziness / Self-preferential bias / Goal drift）+ 六個組合 pattern + 5 個 copy-paste 提示範例，核心洞察：「你不是在配置工具，你是在請 Claude 建工具然後跑它」。

### 核心論點

1. **三大單視窗失敗模式**（Workflow 的存在理由）：
   - **Agentic laziness**：20/50 完成就宣告 done
   - **Self-preferential bias**：模型給自己的輸出打分時偏向自己
   - **Goal drift**：多輪後尤其 context compact 後目標模糊，「don't do X」靜默丟失
2. **動態 vs 靜態 Workflow**：靜態 = SDK 手寫泛化 harness；動態（Opus 4.8）= Claude 為當前任務即時生成客製化 harness
3. **六個組合 Pattern**：Classify-and-act / Fan-out-and-synthesize / **Adversarial verification**（最有用）/ Generate-and-filter / **Tournament**（比較優於打分）/ Loop-until-done
4. **Maker-checker 分離原則**：「no prompt talks it out of self-preferential bias」——只有結構（獨立 checker）才能解決，非意志力
5. **何時跳過**：一般 bug fix 不需要（5 reviewer panel = overkill）；只在「single window 無法完成」時才用

### 關鍵 Copy-paste 提示

- Resume ranking: 80 份履歷 → tournament 排名 → top 10 double-check
- 事實查核: blog draft → claim 提取 → 逐條 check → source 評級（writer 不得自判）
- Slack incident 挖掘: 6 個月 #incidents → root cause 分組（理論從獨立 evidence 生成，再辯論）
- 命名決策: brainstorm 30 → tournament → rubric 選 top 3
- 錯誤→規則: last 50 sessions → 反復修正 → 只保留「真能抓住過去錯誤」的規則

### 批判性觀察

1. **Goal drift 命名填補 workspace 空缺**：subagent-strategy.md §Dynamic Workflow 三失敗模式（agentic laziness / self-preferential bias / goal drift）已被提及，但 goal drift 的具體機制（「each summarization step loses something, and the 'don't do X' you wrote at the start quietly falls off」）此文最清晰
