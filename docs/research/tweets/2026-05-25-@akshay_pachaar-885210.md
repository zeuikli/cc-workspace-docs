## 全文摘要

**定位**：Agent 記憶架構演進（Vector DB → Knowledge Graph → Schema-First Graph）；使用 Pydantic 定義 ontology 解決 LLM extraction 通用化問題；完整 Zep 實作範例 + 設計原則。

### 問題鏈：為什麼 Vector DB 不夠

**Vector DB 失敗場景（Multi-hop Reasoning）**

三個事實存於不同 chunk：
- Alice manages Project Atlas
- Project Atlas runs on PostgreSQL
- The PostgreSQL cluster went down Tuesday

查詢「Alice 的項目是否受到 Tuesday 宕機影響？」需要連接三個 chunk。Vector search 只能找到 1 和 3（都提到相關關鍵詞），遺漏 Fact 2（Alice↔PostgreSQL 的橋梁）。

**Knowledge Graph 解決方案**：實體為 node、關係為 edge、traversal 而非 matching；Chain `Alice → manages → Project Atlas → runs on → PostgreSQL` 讓 multi-hop 可行。

**但 Knowledge Graph 的新問題**：
- 無 schema 時，LLM extraction 自行決定類型（Topic/Object）和關係（RELATES_TO）
- 結果：所有東西都是 "Object"，所有關係都是 "RELATES_TO"，無法精確過濾
- 例子：「哪些企業客戶有 sev-1 開放工單？」→ 圖有數據但無法查詢（沒有類型/嚴重度/計劃層級）

### 解決方案：Pydantic Ontology

**核心原理**：像 FastAPI endpoint 用 Pydantic response model，給 Agent Memory 定義 schema（ontology）

**EntityModel（節點類型）**：

```python
from zep_cloud.external_clients.ontology import EntityModel, EntityText
from pydantic import Field

class Project(EntityModel):
    """
    Represents a specific software project, application,
    or codebase that the user is building or contributing to.
    """
    project_status: EntityText = Field(
        description="Current status: active, completed, paused, or archived.",
    )
    project_type: EntityText = Field(
        description="Type of project: web app, mobile app, API, CLI tool, etc.",
    )
```

**關鍵**：docstring 和 field descriptions 給 extractor 語義信號，讓它正確分類——特別是包含領域術語、產品名稱、行話等訓練數據中沒有的知識。

**EdgeModel（關係類型）**：

```python
from zep_cloud.external_clients.ontology import EdgeModel

class WorksOn(EdgeModel):
    """The user is currently working on, building, or contributing to a project."""
    role: EntityText = Field(description="User's role: lead developer, contributor, etc.")

class UsesTechnology(EdgeModel):
    """The user actively uses or works with a specific technology."""
    proficiency: EntityText = Field(
        description="Proficiency level: beginner, intermediate, advanced, or expert.",
    )
```

**Source/Target 約束（防止任意關係）**：

```python
from zep_cloud import EntityEdgeSourceTarget

client.graph.set_ontology(
    entities={"Project": Project, "Technology": Technology},
    edges={
        "WORKS_ON": (
            WorksOn,
            [EntityEdgeSourceTarget(source="User", target="Project")],
        ),
        "USES_TECHNOLOGY": (
            UsesTechnology,
            [EntityEdgeSourceTarget(source="User", target="Technology")],
        ),
    },
)
```

### Zep 五步 Extraction Pipeline

當有 schema active 時 ingestion 執行：
1. **Entity extraction**：識別文本中的命名實體
2. **Entity resolution**：合並重複（"Nexus" 和 "the Nexus project" → 一個 node）
3. **Fact extraction**：識別關係，輸出 typed edges
4. **Fact resolution**：偵測矛盾，使過期事實失效（保留歷史）
5. **Temporal extraction**：解析時間引用，映射到每個 edge 的 validity window

schema 直接引導步驟 1 和 3。

### Context Template（Prompt 注入格式）

```python
client.context.create_context_template(
    template_id="dev-context",
    template="""# PROJECTS
%{edges types=[WORKS_ON] limit=5}

# TECH STACK
%{edges types=[USES_TECHNOLOGY] limit=10}

# PROJECT DETAILS
%{entities types=[Project] limit=5}

# TECHNOLOGIES
%{entities types=[Technology] limit=10}""",
)
```

輸出：每個條目帶類型、時間標注、屬性；存 template 後按 ID 調用。

### 10/10/10 Constraint（強制領域聚焦）

Zep 強制限制：10 個 entity 類型、10 個 edge 類型、10 個 fields/type。

**設計意圖**：強迫開發者思考「什麼真正重要」而非為所有東西建模。

**Schema as reasoning boundary**：schema 定義 agent 「被允許記住什麼」。不在 schema 中的關係（如 Project → Competitor）不會被創建，即使對話提到了兩者。

與 typed function calling 的類比：
- Function calling：約束 LLM 輸出空間防止無效參數
- Memory schema：約束 LLM 存儲空間防止無效記憶

**建議**：從 3-4 個 entity types + 3-4 個 edge types 開始覆蓋 80% 領域邏輯，增量添加。

## 研究摘要

**TL;DR**：Vector DB → Knowledge Graph → Schema-First Graph 演進；用 Pydantic EntityModel/EdgeModel 定義 ontology 解決 LLM extraction 通用化問題；10/10/10 constraint 強制領域聚焦；schema 是 reasoning boundary（類比 typed function calling）；完整 Zep 實作含五步 pipeline、Context template、Source/target 約束。

### 核心論點

- **Multi-hop failure**：vector similarity 遺漏橋梁 chunk，需 graph traversal
- **Schema-first memory**：無 schema → 通用提取（Topic/Object/RELATES_TO）→ 不可查詢；有 schema → typed extraction → 精確過濾
- **10/10/10 強制聚焦**：約束是設計意圖，而非限制
- **Schema = reasoning boundary**：定義 agent 「被允許記住什麼」，與 typed function calling 同原理
- **Docstring as domain vocabulary carrier**：schema descriptions 攜帶領域術語進 extraction

### 關鍵數據 / 工具

- Zep：EntityModel/EdgeModel/EntityEdgeSourceTarget API
- 五步 Zep extraction pipeline（含 temporal 和 fact resolution）
- 10/10/10 hard constraint（Zep 平台強制）
- Context template 格式（typed + temporally annotated）

### 批判性觀察

- 完整技術實作（Pydantic schema → Zep API → Context template）技術深度本批次最高之一
- 「Schema as reasoning boundary」與 typed function calling 的類比是優雅框架
- 本批次唯一深度聚焦 agent memory 架構（vs 其他文章聚焦 prompting/autonomy）
- Zep 特定 API（非通用 memory 框架）；需要 Zep 訂閱才能完整實作
- 與 workspace 的 MEMORY.md 純文本方法設計哲學不同；但「schema 驅動 extraction」原則值得參考
- Multi-hop failure 診斷清楚，適合向不了解 KG 的人解釋
