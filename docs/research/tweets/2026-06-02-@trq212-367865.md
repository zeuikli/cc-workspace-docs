## 全文

Claude Code's dynamic workflows are the biggest capability upgrade since Skills and Subagents shipped. After deep-diving them with @sidbid, here's what we found.

### What Is a Dynamic Workflow?

Unlike static agent systems where you predefine the orchestration, dynamic workflows let Claude *write the orchestration script on the fly* as a JavaScript file, then execute it.

The result:
- The harness itself becomes a deliverable (saveable, versionable, reusable)
- 100+ parallel agents without context window pollution
- Routing logic is deterministic code, not probabilistic LLM turns

### The Harness Paradigm Shift

Previous Claude Code architecture:
```
You → Claude (orchestrator) → Subagents (workers)
```

With Dynamic Workflows:
```
You → Claude (workflow author) → JS Harness → Agents (workers)
```

The crucial difference: routing and orchestration logic moved from LLM inference to deterministic code. Every conditional, every filter, every worker assignment is now inspectable JavaScript.

This means:
1. **Reproducibility**: Same workflow script = same behavior (unlike pure LLM orchestration)
2. **Auditability**: You can read, modify, and understand the exact orchestration logic
3. **Composability**: Workflows can call skills, which can call subagents
4. **Cost predictability**: Routing doesn't burn tokens

### When to Use Each Tool

| Tool | Use When | Cost Profile |
|------|----------|-------------|
| Ask Claude | One-off question, single context | Low |
| Skill | Repeatable process, reusable recipe | Low |
| Subagent | Task needs own context window | Medium |
| Agent Team | Tasks need inter-agent communication | High |
| /goal | Iterative: loop until done=true | Variable |
| Workflow | Massively parallel, independent tasks | High (predictable) |

### Non-Technical Workflows That Now Make Sense

This is what I'm most excited about.

Before workflows, Claude Code was primarily a coding tool. Now:

**Research synthesis**: Spin up 30 agents, each deep-researching one subtopic, synthesize into one report. Research that would take days → hours.

**Document analysis**: 200-page legal document → 200 agents each analyzing one page in parallel → structured summary in minutes.

**Competitive monitoring**: 50 competitor websites → 50 agents gathering intel → synthesized battle card.

**Customer feedback pipeline**: 500 support tickets → parallel categorization + sentiment → executive summary.

The pattern: anything that's currently "let me read through these 100 things" becomes "let me run a workflow."

### Cost Control Principles

The cost lever is: worker model × worker count × context size per worker.

Best practice pattern (Haiku workers, Opus synthesizer):
```
Orchestrator: Fable 5 / Opus (writes the harness, synthesizes results)
Workers: Haiku (does the parallel work)
```

This gives you:
- Intelligent orchestration (expensive model, single turn)
- Cheap parallelism (Haiku × N workers)
- Intelligent synthesis (expensive model, reads all results)

Rule of thumb: if a task breaks into 10+ independent pieces, workflow + Haiku workers beats Opus doing it sequentially.

### Workflow Anti-Patterns

❌ **Unbounded scope**: "Audit my entire computer" → spawns infinite agents
❌ **Expensive workers**: All-Opus workflow = 100× cost vs Haiku workers  
❌ **No synthesis step**: Raw parallel results without a summarizer = information dump
❌ **forgetting /workflows**: Use `/workflows` to monitor live, pause, and stop runaway agents

### The /workflows Monitor

While a workflow runs, `/workflows` shows:
- All active agents and their current task
- Token usage per agent (real-time)
- Tools being called
- Time elapsed

You can stop individual agents or the entire workflow from here. This is your kill switch.

### Saving and Reusing Workflows

Claude saves the JS file, but check *where* it saves.

Default: somewhere in the global Claude Code working directory (not your project).

Always tell Claude: "Save the workflow script to `.claude/workflows/`"

Then version it in git. A workflow is infrastructure. Treat it like code.

### Nesting: Workflows Inside /goal

The most powerful (and dangerous) pattern:

```
/goal: keep improving product until user satisfaction > 90%
  → runs a workflow each iteration
    → 50 agents analyze user feedback
    → synthesis agent updates product specs
    → main session implements changes
  → /goal checks satisfaction metric
  → loops until done=true
```

This is autonomous product iteration. Set it up carefully. Set explicit stopping conditions. Monitor closely.

### Bottom Line

Dynamic workflows aren't a gimmick. They're a fundamental shift in what Claude Code can parallelize.

The question isn't "should I use workflows?" The question is: "which of my current multi-hour tasks could become multi-minute workflows?"

Start with something bounded. Audit a specific folder. Analyze a specific dataset. Get comfortable with the costs before going large.
