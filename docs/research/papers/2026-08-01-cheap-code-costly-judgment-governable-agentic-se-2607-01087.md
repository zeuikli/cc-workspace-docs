# Cheap Code, Costly Judgment: A Case Study on Governable Agentic Software Engineering

## 摘要 / 核心貢獻

本文轉移了問題焦點：不再問「AI 能否產生程式碼」，而是探討「工程師該如何組織架構、工具、證據與回饋迴圈，使 AI 中介的開發過程保持可檢視、可修正、可維護」。研究者以第一人稱視角進行 12 週個案研究，由一位專家工程師使用前沿 AI coding agent 開發一套文件無障礙修復系統，實證紀錄包含 88 篇同步現場筆記、42 萬行生產程式碼、116 萬行測試/lint/文件/工具程式。

研究提出「治理轉換（governance conversion）」理論——說明高速 AI 實作如何轉為可治理狀態的歷程模型。核心洞見：① **失效驅動治理**——agentic 開發速度會浮現只在實際開發中才顯現的結構性反覆失效，與傳統基於預先設定義務的治理模型不同；② **工程判斷作為控制手段**——人類判斷不會拖慢開發，而是把浮現的失效轉化為持久的治理機制；③ **實務中發現而非預先推導**——控制措施是從真實失效中發現，而非事先從已知需求推導而來。

研究提供可測試的預測，對 AI 輔助時代的軟體工程研究與實務有直接意涵。

## 與 Harness 的關聯

> 2026-08-02 深讀 PDF 原檔後重寫，對齊 v5.1。

**支持面**：「治理轉換」理論與 core.md RECORD「失敗 → `[失敗模式]→[防範]` 入 LESSONS；同簽名重現 ≥2 次才改規則」高度同構。本文的第三項洞見——**控制措施是從真實失效中發現，而非事先從已知義務推導**——正是 v5.1 拿來否決紙上閘門（`qualify-oracle.sh` 儀式、契約欄位 lint）的同一條論據，構成獨立學術背書。

**⚠️ 對 v5.1「單人 → 可刪治理」前提的最強反例**：本文的研究設定是**單一專家工程師、12 週、第一人稱個案**——與本 workspace「單人 workspace 不需團隊級防禦」的前提條件幾乎完全重合。但其結論走向相反方向：在這個單人設定下，工程判斷的價值恰恰體現在**把浮現的失效轉化為持久的治理機制**（durable governance mechanisms），治理構件是隨開發持續**累積**的，而非因為只有一個人就可以省略。

這對 v5.1 的裁決構成一個必須分辨的區別：
- v5.1 刪對的是**協作層**——收據、審計 log、review 尺寸門檻、契約欄位 lint。這些的受眾確實是「要對第三者交代的組織」，本文的單人個案也未產生這類構件。
- v5.1 的風險在**元層與治理層的界線**。本文顯示單人開發者同樣會、也應該長出治理機制（測試 1.16 MLOC vs 生產 420 KLOC，比例 2.76:1 即其具體形態）；差別只在這些機制必須**由真實失效催生**，而非預先設計。v5.1 若把「刪掉預先設計的治理基建」誤讀為「治理構件本身是冗餘」，就走過頭了。

**可引用的量化錨點**：88 筆同步現場筆記 / 12 週 ≈ 每週 7.3 筆，對應 420 KLOC 生產碼；測試與工具程式 1.16 MLOC。可作為評估 workspace `memory/LESSONS.md` 記錄密度是否過稀的外部參照——若 LESSONS 的新增速率遠低於此量級，較可能是「失效未被記錄」而非「失效未發生」。
