Anthropic just dropped 5 workshops, revealing the latest capabilities of Fable 5 — @0xCodez ​

來源: https://x.com/0xcodez/status/2073478036154966486發布日期: 2026-07-04 收錄日期: 2026-07-06 時長: 84:55

Anthropic 在東京 Code with Claude 大會同日發布 Claude Fable 5 與 Mythos 5，5 場工作坊完整呈現能力、基礎設施與部署策略。

整理版（可讀逐字稿） ​

Workshop 1 — Fable 5 能力總覽（00:00–11:22，Diane） ​

大家好，早安東京。我是 Diane，2023 年加入 Anthropic，參與了從 Claude 2 起算的每個版本——共 21 個版本，涵蓋 Haiku、Sonnet、Opus，以及現在的 Fable 和 Mythos。

我們最新的發布就在幾小時前完成。我們推出了 Claude Fable 5 和 Claude Mythos 5，這是第五代模型的第一批。Fable 5 是我們有史以來最強的可公開使用模型，和 Mythos 5 基於相同底層架構。這些模型已在 Anthropic 內部加速我們的工作。

Anthropic 談論很多指數級增長——但這到底意味著什麼？隨著模型智能提升，它能創造的應用價值呈指數增長。今天許多人使用的 agentic coding 比幾年前的自動補全有價值得多。Fable 5 就是這種趨勢的具體體現。

Fable 5 的關鍵優勢——兩個驅動差距的因素：

第一，單次正確率：給 Fable 5 一個複雜、描述清晰的問題，它能一次通過。早期測試者反映，單個 prompt 可以完成原本需要一個團隊花幾天甚至幾週的工作。

第二，長程自主性：Fable 5 能在單一目標下運行數天，全程保持連貫，即使任務跨越數百萬 token，也能記住你的規格說明。它調度 sub-agent 的能力更可靠，且更具成本意識。

Fable 5 不只擅長寫程式碼，它在讀程式碼方面甚至更出色：更擅長排查故障、挖掘 repo 歷史找出問題所在，並主動提出改善建議。在 coding 之外，它也適用於組織實際運轉的工作——財務分析、文件、簡報、試算表——端到端處理，以專業水準回傳成果。

安全機制：Glasswing 計畫始於兩個月前，當時 Mythos Preview 的網路安全能力強到可能被濫用，因此只開放少數合作夥伴。之後我們建立了新的安全保護系統：當請求觸及網路安全、生物或化學主題時，Fable 會路由到 Opus 4.8 處理，回應明確標注，計費按 Opus 定價。這讓最強模型能在今天（而非幾個月後）交到所有人手中。

早期客戶反饋：Rakuten 表示最高 effort 下 Fable 5 能驗證自己的工作，讓自主自動化操作成為可能；Cognition 在其 Frontier Bench 上 Fable 5 得分最高，強調長程推理和對陌生工具的泛化能力；Jen Spark 表示 Fable 5 在所有測試模型中排名第一，在 UI 設計和遊戲 coding 等最難任務上表現尤為突出。

Mythos 5（解除網路安全/生物安全限制的版本）今日開放給 Glasswing 合作夥伴；本月稍後將向生命科學研究者開放，因為讓生物技術風險的同一種能力，正是 AI 在這個領域產生最大正向影響的能力。

開發建議：

  1. 為下一版 Claude 設計，而非當前版本——勝出的開發者架構、harness 和產品體驗能夠吸收下一輪智能跳躍。
  2. 建立更難的 evals 和產品原型，測試目前尚不可行的體驗。當某個任務開始奏效，那是出貨魔法產品的訊號。
  3. 讓 model 升級變得簡單：自動化 eval、測試流程，將 model 升級視為商業機會。

Workshop 2 — 能力曲線（11:22–30:54，Theo） ​

我是 Theo，負責長程能力（長上下文和記憶）。大約兩年前加入，那時 Sonnet 3.5 剛剛發布，agents 幾乎還不是個詞，模型能做 coding 只是生命跡象。去年此時 Opus 4 剛發布，Claude Code 還未 GA。現在我們有了 Fable、Mythos 和 Opus 4.8。

指標觀察：在場超過半數的人認為 Claude 讓他們效率提升 10 倍。Anthropic 內部超過 80% 的程式碼由 Claude 合並。

SWE-bench 能力曲線：

模型SWE-bench Verified備注
Sonnet 3.762%12 個月前
Opus 4.888%現在
Fable/Mythos飽和benchmark 已不夠難

從 62% 到 88% 意味著舊模型的失敗率是新模型的 3 倍。demo 中 Sonnet 4 重建 Claude.ai 網站時直接行動、不規劃，結果無法完全運作；Opus 4.8 先規劃再執行，最終用更少 tool 呼叫、更少行程式碼完成，且結果完全正確。

三大智能躍升：

1. 先規劃後執行：舊模型像沒看說明書就組裝 IKEA 家具，直接衝進去然後失敗。新模型先思考規格再執行，途中自我修正（說「actually」或「never mind」），首次執行就更高效。開發建議：允許模型先思考，在 UX 中給予 adaptive thinking 空間，使用 effort dial。

2. 錯誤恢復與自我修正：舊模型遇到反饋後一遍遍重複相同的失敗方案，即 "doom looping"。新模型真正看反饋並嘗試不同方法，往往帶來更好結果，且廢棄 token 更少。開發建議：設計能給模型反饋的環境（tool 或人類回饋）。

3. 長程連貫性：舊模型中途忘記任務、丟失規格，即「losing the plot」。現在模型能維持到百萬 token 的連貫性。開發建議：可以放手給整個 codebase 而非單一檔案，無需再大量切分上下文。

客戶驗證：Shopify 認為 Opus 4.8 錯誤恢復和規劃明顯改善；Cursor 發現工具呼叫和 token 效率大幅提升；Cognition 表示 Opus 4.8 更自主、能運行更長時間、更省 token。

戰術建議（如何為不斷進化的模型開發）：

心態轉變：要有野心，測試 Claude 今天做不到的事，而非只測 12 個月前能做的事。

  1. 建立/更新 evals：eval 是 AI 時代的單元測試；創建今天模型尚未飽和的測試案例；如果 eval 不動了，表示它可能已飽和，是時候更新了。

  2. 縮短 scaffolding：提示寫的是意圖，而非針對舊模型所有失敗的 workaround。系統提示中的過時指令可能讓新模型錯誤遵循。精簡 scaffolding，讓模型展示它能做什麼。

  3. 給模型空間：使用 adaptive thinking 和 effort dial；讓 agent 有更多 environment 訪問權限（用 classifier 控制，如 auto mode in Claude Code）；閉合 agent loop——給模型驗證輸出的手段（如 computer use tool 做 QA）。

Workshop 3 — Claude Managed Agents（30:54–44:29，Jess + Michael） ​

背景：隨著模型能力指數級增長，瓶頸越來越是基礎設施而非智能本身。

能力演進時間線：

  • 2 年前（Opus 3）：寫並測試單一 component，幾分鐘
  • 去年（Claude 4）：debug 整套檔案，約一小時，重度人工引導
  • 今年（Fable 5）：整夜運行，跨 agent 團隊，處理整個 linear backlog
  • 不久的將來：整個 M&A pipeline 端到端自主完成

開發者痛點（發布前調查）：

  • Context management：何時放入何種 context 難以調校
  • 基礎設施：bursy workload、不可預測計算模式、難以安全擴展
  • 觀測性：非確定性模型輸出大量非結構化資料，難以判斷品質

Claude Managed Agents 核心架構：

Agent（系統提示 + 模型 + skills + tools）
  + Environment（網路允許清單 + 預裝包）
  = Session（自動配置 sandbox，掛載憑證）
  → Events（agent 動作 + user 輸入）

Events 類型：

  • User events：你發送給 agent 的引導
  • Agent events：agent 的行動（訊息、工具執行、context compaction、委派給其他 agent）
  • Session events：工作單元的生命週期（狀態轉換、錯誤、成果）
  • Span events：關聯事件的聚合檢視

Pascal demo（假想線上雜貨外送服務）：agent 分析訂單資料提供洞見（熱銷商品、訂單高峰時段、復購預測）。在 Claude Console 可即時看到所有 events，debug agent 可進一步優化。

進階功能（最新發布）：

  • Multi-agent orchestration：委派給獨立 context window 的子 agent 並行處理
  • Outcomes：給定出口條件或 rubric，Claude 持續迭代直到達標
  • Memory：跨 session 讀寫記憶，不再每次從零開始
  • Dreaming：基於 memory，對學習內容反思並蒸餾為精煉記憶
  • Self-hosted Sandboxes：agent loop 和工具執行在你的基礎設施中，檔案和包不離開你的邊界
  • MCP Tunneling：訪問不想暴露到公開網路的私有 MCP server
  • Scheduled Deployments：設定循環排程自動觸發新 session
  • Vault：opaque 佔位符取代真實 secret token，Claude 使用時看不到實際憑證

Workshop 4 — Claude Code 實際應用（44:29–57:43） ​

使命：縮短「想法→上線產品」之間的距離，透過工具從模型中引出前沿智能，讓每個 builder 都能用上。

介面演進：

  • CLI（power user，最大控制和自訂）
  • IDE（跟隨所有程式碼變更）
  • Claude Code on Desktop（全螢幕 GUI，內建預覽、Sidebar、rich output 渲染；跨所有本地和雲端 session 的統一視圖）
  • Agents View in CLI（不離開終端的控制平面）
  • iOS / Android（遠端控制，移動辦公）

VS Code IDE extension 和 Desktop app 都基於 Claude Agent SDK（與很多人正在構建的相同 SDK）。

新功能（回應開發者反饋）：

  • Code Review：部署一組 agent 捕捉 PR 中的關鍵 bug，Anthropic 所有內部團隊每天使用
  • Mobile（iOS/Android）：遠端控制，不再需要隨身半開著筆電
  • Routines：配置一次，按排程/webhook/API 呼叫自動觸發 Claude Code 任務
  • Claude Security：隔夜掃描 codebase，標記漏洞（含最關鍵項），一鍵啟動 Claude Code session 修復
  • Dynamic Workflows：在確定性結構下並行跑數十到數百個 agent

Dynamic Workflows demo（13 語言本地化）：

  • 串行方式：每語言 3 分鐘，13 種語言需近 1 小時 + 大量手動 prompting
  • 並行方式：1 個 prompt → workflow 建立 12 個並行翻譯 agent + 12 個驗證 agent，在 Desktop app 側欄可見全部同步運行
  • 工作流可保存為 JavaScript 供未來複用

企業採用：

  • Spotify：月合並 1,000+ PR，遷移時間縮短 90%（基於 Claude Agent SDK 的背景 agent，讀英文遷移計畫自動開 PR）
  • Mercari（日本 C2C 平台）：整個工程團隊使用 Claude Code，工程產出同比增長 90%
  • Anthropic 內部：工程師平均出貨程式碼量是以往的 8 倍

Workshop 5 — 部署：效能、成本、可靠性（57:43–84:55） ​

Prompt Caching（最重要的單一優化）：

長程 agentic 應用有大量工具呼叫和用戶輪次，上下文很長，每次請求都重複發送這些長段。Prompt caching 讓我們預計算共用的上下文部分（KV 值），存在服務器上；下一個請求只需計算前次的小增量。

好處：

  • 90% 折扣（只付 10%）
  • 更快的回應時間
  • 快取 token 不計入 rate limit

目標：cache hit rate ≥ 80%（Perplexity、Cursor、Replit 等已達很高命中率，這是它們能被服務的前提）。

工具：

  1. Claude Console cache dashboard：查看 agent 的 cache hit rate（示範中從 0% → 58%，一個小改動就到位）
  2. Claude API skill（Claude Code 預裝）：直接說「improve my cache hit rate」，它會修改 prompt 並加入 cache 控制標頭

Context Engineering（三招管理上下文）：

1. Tool Search Tool：

問題：100+ 個工具全部載入上下文，佔用大量 context，但每次運行可能只用其中 10%。 解法：只載入 1 個工具——Tool Search Tool。模型需要工具時先問它，它從庫存中找到對應工具並載入。 效果：Lovable 減少 10% token 用量，且因模型 context 更乾淨，智能表現也提升。

2. Programmatic Tool Calling：

問題：工具回傳大量資料（100 封 email、完整 HTML 頁面），全部放入 context，但可能只需要一個標頭或一個 div。 解法：讓模型看到資料結構後，即時寫程式碼抽取所需的 5% 資料放入 context，其餘丟棄。 效果：Quora 的 HTML 解析 agent 大幅改善（原本拉完整 HTML 頁面，改為只取所需片段）。

3. Compaction：

問題：即使做了上述優化，長時間運行的 agent（數小時到數天）仍會耗盡上下文。 解法：開發者設定閾值（如 400K），接近時暫停 agent，用另一個模型摘要整個 transcript（移除已無需的中間工具結果），清空上下文放入緊湊摘要，agent 無縫接著跑。 效果：Hex 早已自建類似機制，改用平台版本後刪除了 300 行程式碼。

HeroCorp Demo（綜合展示）：

  • CEO dashboard，4 個業務目標，原本用 Opus 4.8 消耗百萬 token 只完成 1 個目標
  • 啟用 Tool Search Tool + Programmatic Tool Calling + Compaction（設 400K 閾值）後，所有 4 個目標全部完成，用量大幅下降
  • 細節：Tool Search Tool 先查詢「hero retention metrics」再精確呼叫；Gong 會議轉錄工具回傳全文，programmatic tool calling 只抽取情感分析結果；Compaction 從 9K 清回 10K，並給出清晰的「已收集資料 + 待完成事項」摘要

Advisor 策略（成本 + 品質兼顧）：

原理：就像讓初級工程師能問資深工程師幾個問題，效率大幅提升，資深工程師只付出一點時間成本。 做法：Sonnet/Haiku 做工具呼叫（擅長且便宜），給它一個工具讓它能向 Opus/Fable 諮詢（只在需要深度推理時呼叫）。 效果：HeroCorp demo 中，Sonnet 認為某個都市協議「綠燈/正常」，但 Opus advisor 發現 Gong 轉錄底部埋著「市長想要 Cryo Thing 出席開幕式」的訊息——帳戶團隊漏掉了，Opus 標記為紅色警示，最終讓 CEO 重新排期，成功挽救交易。 節省：用便宜模型處理大部分工作，昂貴模型只在需要差異化推理時介入。

其他 2026 年新功能：

  • WIF（Workload Identity Federation）：消除 API key，改用工作負載身分聯合，杜絕 key 洩漏風險
  • Model Fallback：Fable 5 安全分類器擋住請求時，Messages API 自動回退到備援模型清單，提升可靠性

以上只是 2026 年上半年發布的部分功能，而我們才過了半年。
